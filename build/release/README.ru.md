# Сборка выпуска формата 1

Инструменты издателя запускаются из проверенной копии исходников от обычного
пользователя. Нужны Python 3.10+, PyYAML и Git. Для сборки и просмотра профилей
также нужен Docker Compose с выводом config в JSON. Сверка установленного кода
работает без Git. [Контракт выпуска](../../docs/UPDATES.ru.md) · [English](README.md)

## Посмотреть зависимости

Укажите полный commit. Сборщик читает объекты Git. Локальные правки и .env
рабочей копии в архив не попадают. Compose вычисляет конфигурацию выбранной
роли во временном каталоге со значениями из зафиксированного env.example.

```sh
python3 build/release/package.py pins --commit 06a01e9dea81402cfbb4366fff009d478cc65042 --llm deepseek-v4-flash-vision --mode stack
```

Для каждого сервиса выводится образ с digest, для каждой модели — репозиторий
и полная ревизия весов. В stack видны обе роли и пересылки head. Короткие имена
Docker Hub разворачиваются в полные. Для отдельного бинарника Compose используйте
--compose-bin.

## Подготовить входные данные

Издатель передаёт рецепт в JSON. Требования к хосту и разрешённые переходы
берутся из результатов испытаний конкретного выпуска.

| Поле | Содержимое |
|---|---|
| version, sequence, created_at | Версия, номер выпуска и фиксированное время UTC |
| code_urls | Адреса HTTPS архива кода или пустой список при локальной доставке |
| profiles | Список профилей с id, llm, mode, requirements. Для каждой роли указаны python_min, docker_min, compose_min, driver_min и min_total_ram_bytes |
| transitions | Проверенные источник, целевой профиль, impact, списки перезапусков, backup, migration и rollback по контракту выпуска |

Отдельно передаются JSON-массив описаний image/model формата 1 и каталог
с подготовленными архивами по их путям payload. Для образа нужны закреплённая
ссылка и config digest, для модели — ревизия и инвентарь файлов. Сборщик находит
описания по вычисленной конфигурации, проверяет размер и хеш каждого выбранного
архива, для весов — ещё и файлы внутри. Соответствие config/layers образу
требует подтверждения издателя и испытания импорта в U5. Проверка полей рецепта
не доказывает совместимость данных при запуске новой версии приложения.

## Собрать и подписать

```sh
python3 build/release/package.py build --commit "$COMMIT" --recipe recipe.json --dependencies dependencies.json --store ./artifacts --output ./release-out
```

Укажите новый выходной каталог. После проверок в нём появятся release.json и
payload/code.tar.gz. Порядок файлов, время и права фиксированы, исполняемость
берётся из Git. Одинаковые входные данные и версия средств сжатия дают одинаковые
байты. Архивы зависимостей остаются в каталоге артефактов для офлайн-поставки.

После просмотра манифеста подпишите его на машине издателя отдельным ключом
выпусков. Открытый ключ распространяется по доверенному каналу.

```sh
ssh-keygen -Y sign -f "$RELEASE_KEY" -n ragspark-release-v1 release-out/release.json
```

Файл release.json.sig появится рядом с манифестом. Публикация и подпись указателя
stable-канала выполняются отдельно.

## Сверить старую установку

Эталон содержит проверенный commit и SHA256 канонического списка файлов.
Для e09da62 в нём 45 файлов. Эталон фиксирует исходный код установки.
Совместимость перехода на конкретный выпуск издатель подтверждает отдельно.
Команде нужен доступ на чтение VERSION, manifest.json и файлов поставки.

```sh
python3 build/release/package.py compare --installed /opt/ragspark --baseline build/release/baselines/e09da62.json --commit e09da628575d0245ed3afe2524e19ce34b7dfc97 --inventory-sha256 ed1c6ea18e863e84d284f4113402118b1e27dead64943f8445cf366628d15bba
```

Код выхода 0 означает совпадение файлов, прав и двух записей версии. При
расхождении или невозможности проверки код выхода 3. В отчёте видны пропавшие,
изменённые и лишние пути в каталогах поставки. Рабочие env и каталоги кэша
байткода исключены. Устаревшая версия в manifest.json отмечается даже при
совпадении кода. Сверка только читает файлы и предполагает стабильное дерево.
Перед обновлением её нужно повторить под блокировкой обслуживания.

Для другой исходной версии используйте **baseline --commit FULL_COMMIT --files**.
После проверки сохраните commit и хеш инвентаря в доверенном источнике.
Хеш, полученный из того же непроверенного файла, не устанавливает доверие.
