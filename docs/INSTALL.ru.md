# Установка RAGSpark

[English version](INSTALL.md)

Установщик разворачивает режим `single` на одном DGX Spark и режим `stack` на
двух (см. «Режим stack» ниже). Он проверяет систему, скачивает недостающее, создаёт настройки со случайными паролями,
добавляет системную службу, которая запускает стек при загрузке, запускает
его, регистрирует модели в RAGFlow и завершает работу приёмочной проверкой:
пример документа индексируется, и чат должен ответить на вопросы по нему со
ссылкой на источник. Запись о решении: D18 в [DECISIONS.ru.md](DECISIONS.ru.md).

## Требования

| | |
|---|---|
| Машина | NVIDIA DGX Spark (GB10, 128 ГБ общей памяти) |
| Система | DGX OS 7.x с Docker, модулем Compose и NVIDIA container runtime (всё предустановлено) |
| Драйвер | NVIDIA 580.x |
| Python | 3.10 или новее (в DGX OS — 3.12) |
| Диск | около 60 ГБ под образы и веса моделей, плюс место под документы |
| Сеть | Docker Hub, `ghcr.io` и `huggingface.co` — или зеркало реестра и заранее скопированные веса |
| Порт | свободный 80 или любой другой |

Веб-интерфейс и API работают по обычному HTTP: ставьте RAGSpark в доверенной
сети. Для доступа извне поставьте перед веб-портом свой обратный прокси с TLS.

## Установка

```bash
git clone https://github.com/0ffch41n/ragspark.git
cd ragspark
sudo ./install.sh
```

Установщик спрашивает язык, e-mail суперпользователя (по умолчанию
`admin@ragspark.local`), веб-порт (80), каталог для весов моделей
(`/srv/ragspark/hf-cache`) и, если их несколько, LLM. Затем проверяет систему,
показывает, что будет создано, и просит подтверждения. До этого на машине
ничего не меняется.

Меню LLM строится по [catalog/models.yaml](../catalog/models.yaml): скорость
для одного пользователя, контекст, память, инструменты и зрение, лицензия и то,
прошла ли модель приёмочную проверку (*проверена*) или ещё нет
(*экспериментальная*). Введите номер или имя; Enter берёт модель по умолчанию,
её же берёт `--yes`. В плане перечислены все модели, которые будут скачаны, с
лицензиями. `./install.sh --llm list` показывает меню и ничего не устанавливает.

Если веса уже скачаны, установка занимает около 15 минут, из них 10 — запуск
моделей. Первая установка вдобавок скачивает около 60 ГБ.

Без вопросов:

```bash
sudo ./install.sh --yes --lang ru --admin-email admin@example.com --http-port 8080
```

| Параметр | Действие |
|---|---|
| `--lang ru\|en` | язык сообщений; он же язык примера чата |
| `--yes`, `-y` | отвечать «да» на все вопросы, брать значения по умолчанию |
| `--admin-email` | e-mail суперпользователя |
| `--http-port`, `--http-bind` | веб-порт и адрес, на котором он слушает (по умолчанию `0.0.0.0`) |
| `--models-dir` | каталог для весов моделей |
| `--llm` | файл LLM из `compose/llm/` без `.yaml`; `--llm list` показывает модели |
| `--role head\|node` | режим stack: `node` ставит второй узел (см. «Режим stack»); `head`, по умолчанию, — обычная установка |
| `--head-ip`, `--node-ip` | режим stack: адреса на кабеле (по умолчанию `192.168.100.10` и `192.168.100.11`) |
| `--skip-acceptance` | пропустить приёмочную проверку; чат «Ассистент» всё равно создаётся |
| `--no-network` | пропустить проверку задержки реестров |
| `--force` | продолжать, несмотря на проваленные проверки (см. «Проверки») |

`sudo` не передаёт переменные окружения. Зеркало или прокси для скачивания
весов указываются в той же командной строке; токен Hugging Face читается без
вывода на экран и передаётся по имени, поэтому не попадает ни в список
процессов, ни в историю оболочки:

```bash
sudo HF_ENDPOINT=https://hf-mirror.example HTTPS_PROXY=http://proxy:3128 ./install.sh
read -rs HF_TOKEN && export HF_TOKEN
sudo --preserve-env=HF_TOKEN ./install.sh
```

Модели по умолчанию публичные, токен им не нужен. Образы Docker скачивает по
своим настройкам; зеркало реестра описано в [BUILD.ru.md](BUILD.ru.md).

## Шаги

| № | Шаг | Что происходит |
|---|---|---|
| 1 | Проверка системы | см. «Проверки» |
| 2 | План | что будет создано; подтверждение |
| 3 | Файлы | установка в `/opt/ragspark`; команда `ragspark` |
| 4 | Настройки и пароли | `compose/.env` со случайными паролями (права 600), выбранные настройки, `docker compose config` |
| 5 | Образы контейнеров | недостающие скачиваются, по три попытки |
| 6 | GPU в контейнере | `nvidia-smi` в образе vLLM |
| 7 | Веса моделей | проверка без сети; недостающие скачиваются |
| 8 | Системная служба | `ragspark.service`, включена |
| 9 | Таймер присмотра за парой | `ragspark-watch.timer`, включён: каждые 30 с держит вместе две половины LLM режима stack, в режиме single ничего не делает (см. «Режим stack») |
| 10 | Запуск стека | по порядку, около 10 минут |
| 11 | Модели в RAGFlow | LLM, эмбеддинги и реранкер зарегистрированы и назначены по умолчанию |
| 12 | Приёмочная проверка | см. «Приёмочная проверка» |

Веса скачивает временный контейнер из образа vLLM, в котором уже есть
`huggingface_hub`; на хост ничего не ставится. Берутся только файлы, которые
загружает vLLM (`*.safetensors`, конфигурация, токенизатор), без дублирующих
копий `*.bin` и `*.onnx`, которые лежат в некоторых репозиториях. Каждая
модель берётся в той ревизии, которую закрепляет её файл compose
(`--revision`, проверенный коммит), а не в том виде, в каком репозиторий
лежит сегодня. Веса, уже лежащие в каталоге, используются повторно.

Любой шаг можно повторить. Если установка прервалась — не скачался образ,
машина перезагрузилась, нажали Ctrl+C, — запустите `sudo ./install.sh` ещё
раз: он продолжит с настройками первого запуска, а пройденные шаги займут
секунды.

Журнал — `/opt/ragspark/install.log` (права 600, паролей в нём нет).

## Проверки

| Проверка | FAIL | WARN |
|---|---|---|
| Архитектура, Python | не aarch64, Python старше 3.10 | |
| GPU, драйвер | нет `nvidia-smi` | не GB10; драйвер не 580 |
| Память | меньше 90 GiB | меньше 110 GiB |
| Docker, Compose | нет или старше 24.0 / 2.24 | |
| NVIDIA runtime | | не значится в Docker (на шаге 6 проверяется контейнером) |
| Диск | свободно меньше 25 ГБ | свободно меньше 100 ГБ |
| Порт | занят | |
| Реестры | | недоступен; TLS-рукопожатие дольше 5 с (Docker сдаётся через 10 с) |
| Прежние установки | см. ниже | |

`--force` позволяет продолжить при FAIL, кроме проверок, которые защищают
существующие данные. Они останавливают установщик в любом случае:

- `/opt/ragspark` или `/etc/systemd/system/ragspark.service` существует, но
  создан не установщиком;
- есть контейнеры стенда RAGSpark, запущенного вручную (из каталога
  `compose/`);
- есть тома прежнего стенда: их базы данных принимают только пароли из `.env`
  того стенда.

В сообщениях указана команда, которая решает каждый случай. Удаление томов
удаляет их документы, пользователей и чаты.

`sudo ./install.sh check` выполняет только проверки.

## Что создаётся

| Где | Что |
|---|---|
| `/opt/ragspark` | `compose/`, `tools/`, `installer/`, `acceptance/`, `catalog/`; `compose/.env` с паролями; `manifest.json`; `install.log` |
| `/srv/ragspark/hf-cache` | веса моделей (или выбранный каталог) |
| `/etc/systemd/system/ragspark.service` | запуск стека при загрузке |
| `/etc/systemd/system/ragspark-watch.service`, `.timer` | запускают `ragspark watch` каждые 30 с |
| `/usr/local/bin/ragspark` | команда управления |
| Docker | проект `ragspark`: 8 контейнеров, 6 томов, сети `ragspark` и `ragspark-backend`; образы |

Не меняются: `/etc/docker/daemon.json`, системные пакеты, файрвол, DNS, другие
контейнеры. В `manifest.json` записано всё, что создал установщик, и удаление
убирает ровно это.

После установки клон репозитория больше не нужен. Стек работает из
`/opt/ragspark/compose`; не запускайте вдобавок каталог `compose/` клона — это
тот же проект `ragspark`.

## После установки

Установщик выводит адрес, логин и команду, которая показывает пароль:

```bash
sudo grep ^ADMIN_DEFAULT_PASSWORD= /opt/ragspark/compose/.env | cut -d= -f2
```

Готовы два чата:

| Чат | База знаний | Для чего |
|---|---|---|
| «RAGSpark — пример» («RAGSpark sample» при `--lang en`) | памятка-пример | рабочий пример с настройками RAGSpark |
| «Ассистент» («Assistant» при `--lang en`) | нет | общие вопросы, на которые отвечает сама модель; она не знает ни ваших документов, ни интернета |

Базу знаний и чат примера можно удалить в веб-интерфейсе;
`sudo ragspark acceptance` создаёт их снова и заменяет базу знаний или чат с
тем же именем. Чат ассистента создаётся один раз и дальше не трогается вместе
с его разговорами; если его удалить, `sudo ragspark acceptance` создаст его
снова.

Новые базы знаний для русских документов: язык *Russian*, парсер PDF
*Plain Text* (D14 в [DECISIONS.ru.md](DECISIONS.ru.md)). Модели уже назначены
по умолчанию.

Для **отсканированных** PDF — документов без текстового слоя — парсером PDF
выберите вместо этого зрячую модель `qwen3.8-27b` (экземпляр
`ragspark-vision`). Она читает каждую страницу как картинку той же LLM, что
отвечает в чате: около 17 с на страницу, и пока идёт индексация, чат отвечает
медленнее. Для любого PDF с текстовым слоем оставляйте *Plain Text*: так
быстрее, и текст читается точно.

**Пользователи.** Регистрация выключена: веб-интерфейс её прячет, а сервер
тоже отклоняет запросы на регистрацию (`REGISTER_ENABLED=0`, проверено в
[VALIDATION.ru.md](VALIDATION.ru.md), раздел 11). Новых пользователей создаёт
суперпользователь через сервис администрирования (`/api/v1/admin/users`),
который отвечает только после его входа. Не настраивайте вход через внешний
сервис (OAuth, OIDC), не ограничив, кто может им пользоваться: RAGFlow создаёт
учётную запись любому, кто вошёл через настроенного провайдера, — независимо
от того, включена ли регистрация.

### Уровни рассуждений

Список под полем ввода чата задаёт, как чат ищет ответ. Он начинается с
«Naive»; браузер запоминает выбор.

| Уровень | Как отвечает | Время ответа¹ |
|---|---|---|
| Naive | один поиск с настройками чата и один ответ; если ничего не прошло порог — текст чата «нет ответа» | 3–8 с |
| Low | агентный конвейер RAGFlow: ключевые слова из вопроса, поиск, проверка результата | 15–20 с |
| Medium, High | то же, но с бо́льшим числом поисков и черновиков и проверкой, хватает ли сведений | около 1–2 мин |
| Ultra | больше всего раундов | около 1–2 мин |

¹ DGX Spark с моделью по умолчанию, на наборах вопросов RAGSpark
([VALIDATION.ru.md](VALIDATION.ru.md), раздел 8).

Naive достаточно, когда ответ находится в одном месте документов; уровни
выше — для вопросов, где нужно свести вместе несколько фрагментов. Они пишут
ответ своими словами, поэтому на вопрос, ответа на который в документах нет,
могут ответить «в документах нет информации о …», а не текстом чата «нет
ответа». Обоснование — D19 в [DECISIONS.ru.md](DECISIONS.ru.md).

| Команда | Действие |
|---|---|
| `sudo ragspark status` | версия, адрес, служба, контейнеры, состояние RAGFlow |
| `sudo ragspark start` | запустить и дождаться готовности всех сервисов; запускает только недостающее |
| `sudo ragspark stop` | остановить; данные сохраняются. При следующей загрузке стек запустится снова |
| `sudo ragspark restart` | остановить и запустить, около 10 минут |
| `sudo ragspark logs [сервис] [--tail N]` | журналы: `ragflow`, `vllm-llm`, `vllm-embed`, `vllm-rerank`, `es01`, `mysql`, `minio`, `redis` |
| `sudo ragspark llm [имя]` | показать LLM или сменить её: чат ждёт около 7–10 минут, веб-интерфейс — около минуты; см. [COMPOSE.ru.md](COMPOSE.ru.md), «Смена LLM». Ещё переключает режимы single и stack (на головном узле) |
| `ragspark watch` | запускается таймером каждые 30 с, не вручную: держит вместе половины LLM режима stack, с предохранителем памяти (см. «Режим stack») |
| `sudo ragspark acceptance` | повторить приёмочную проверку |
| `sudo ragspark check [--gpu-reload]` | проверка системы; см. «GPU после перезагрузки systemd» |
| `sudo ragspark backup [--wait-minutes N]` | сохранить данные на head; временный перерыв RAGFlow |
| `sudo ragspark backup --list` | локальные копии или принятые копии на настроенном node |
| `sudo ragspark backup --schedule on` / `off` | включить/отключить ночной бэкап head |
| `sudo ragspark backup --sync` | повторить передачу на второй узел без остановки сервисов |
| `sudo ragspark restore NAME` | заменить данные на head после проверок, подтверждения и страховочной копии |
| `sudo ragspark uninstall` | удаление; см. «Удаление» |

`--lang` и `--yes` работают с любой командой.

## Запуск при загрузке

`ragspark.service` выполняет `docker compose up -d --wait` и не задерживает
загрузку. RAGFlow стартует после моделей, поэтому веб-интерфейс открывается
примерно через 10 минут после загрузки; ход запуска показывает
`sudo ragspark status`.

Docker сам запускает часть контейнеров, когда стартует: те, у которых
последний код выхода не 0 (политика перезапуска `on-failure`; контейнер, убитый
после таймаута остановки, выходит с 137, Elasticsearch — с 143; после
отключения питания неудачными считаются все). Запущенные вместе, модели
оставляют друг друга без памяти. Поэтому служба сначала останавливает
контейнеры, которые работают, но не готовы, а затем запускает всё по порядку.

## Приёмочная проверка

[tools/acceptance.py](../tools/acceptance.py) работает внутри контейнера
RAGFlow и проходит всю цепочку:

1. создаёт базу знаний с настройками RAGSpark (текстовый слой PDF, фрагменты
   по 512 токенов) и загружает `acceptance/sample-ru.pdf` — одностраничную
   вымышленную памятку по серверу;
2. ждёт разбора и проверяет, что фрагменты — русский текст (не меньше 80%
   кириллических букв);
3. создаёт чат с реранкером, весом векторов 0.7 и порогом 0.1 (D15);
4. задаёт два вопроса с известными ответами — ответ должен содержать нужные
   факты, ссылаться на документ и не содержать китайских или японских знаков —
   и один вопрос, на который в документе ответа нет: на него чат должен выдать
   свой текст «нет ответа»;
5. задаёт первый вопрос ещё раз на уровне Low, через агентный конвейер,
   который должен ответить так же и не дольше 5 минут;
6. создаёт чат «Ассистент», если его нет, и проверяет, что он отвечает на
   простой вопрос.

Разговоры, которые открыла проверка, она удаляет, так что чаты начинаются
пустыми.

PDF воспроизводимо генерируется из `acceptance/sample-ru.md` скриптом
`acceptance/make_sample.py`; вопросы — в `acceptance/sample-ru.json`.

## GPU после перезагрузки systemd

С драйвером cgroup `systemd` в Docker команда `systemctl daemon-reload` (её
выполняют обновления пакетов) может отнять GPU у работающих контейнеров:
`nvidia-smi` в них выдаёт `Failed to initialize NVML: Unknown Error`. Это
известная проблема NVIDIA Container Toolkit. Установщик перезагружает systemd
до запуска моделей и не меняет настройки Docker. Проверьте машину:

```bash
sudo ragspark stop                  # проверка перезагружает systemd; стек не должен работать
sudo ragspark check --gpu-reload    # до установки: sudo ./install.sh check --gpu-reload
```

Проверка запускает контейнер с GPU, перезагружает systemd и снова проверяет GPU
внутри контейнера. Если она сообщает о потере, переключите Docker на драйвер
`cgroupfs`. Команды ниже сохраняют существующий `/etc/docker/daemon.json` (DGX
OS регистрирует в нём NVIDIA runtime) и делают его копию:

```bash
sudo cp -a /etc/docker/daemon.json /etc/docker/daemon.json.bak
sudo python3 - <<'EOF'
import json
p = "/etc/docker/daemon.json"
cfg = json.load(open(p))
opts = [o for o in cfg.get("exec-opts", []) if not o.startswith("native.cgroupdriver=")]
cfg["exec-opts"] = opts + ["native.cgroupdriver=cgroupfs"]
json.dump(cfg, open(p, "w"), indent=2)
EOF
sudo systemctl restart docker       # останавливает все контейнеры на машине
sudo docker info --format '{{.CgroupDriver}}'
sudo ragspark check --gpu-reload
sudo ragspark start
```

## Режим stack

Два DGX Spark запускают одну LLM, которая не помещается ни в один из них:
DeepSeek V4 Flash, примерно вдвое быстрее LLM по умолчанию, на тестовых
наборах RAGSpark отвечает так же (D10 в [DECISIONS.ru.md](DECISIONS.ru.md),
[VALIDATION.ru.md](VALIDATION.ru.md), разделы 17–18). Первый узел,
*головной*, — обычная установка с RAGFlow; второй, *узел*, запускает другую
половину LLM, эмбеддинги и реранкер. Как разложены сервисы:
[COMPOSE.ru.md](COMPOSE.ru.md), «Режим stack».

**Требования сверх обычных**

| | |
|---|---|
| Кабель | один кабель QSFP между узлами, настроенный по [руководству NVIDIA для двух Spark](https://build.nvidia.com/spark/connect-two-sparks/stacked-sparks): 200 Гбит/с, MTU 9000, оба порта RoCE активны |
| Адреса | `192.168.100.10` на головном узле, `192.168.100.11` на узле (другие — `--head-ip`, `--node-ip`), сохраняются после перезагрузки |
| Память | около 92 GiB на каждом узле для его половины LLM |
| Диск | ещё около 190 GB на каждом узле: каждый читает свою копию весов (168 GB), плюс образ |

**1. Поставьте узел** — на втором Spark, из клона репозитория:

```bash
sudo ./install.sh --role node
```

Установщик проверяет кабель (останавливается, если ни у одного интерфейса нет
адреса узла), скачивает образы и веса LLM режима stack, эмбеддингов и
реранкера, ставит `ragspark.service` и таймер присмотра и запускает стек.
После этого эмбеддинги и реранкер отвечают на кабеле, порты 8001 и 8002;
половина LLM на узле ждёт головной узел. В локальной сети ничего не слушает.
У узла нет веб-интерфейса и данных.

**2. Переключите головной узел** — на установленном головном узле LLM
меняется командой:

```bash
sudo ragspark llm deepseek-v4-flash-vision
```

Новый головной узел ставится сразу с ней: `sudo ./install.sh --llm
deepseek-v4-flash-vision`, после узла. Прежде чем что-то менять, команда
проверяет кабель и модели узла; затем прежняя LLM останавливается, пересылки
берут на себя эмбеддинги и реранкер (поиск останавливается примерно на
минуту), и обе половины загружаются. В первый раз чат снова отвечает примерно
через 10 минут; команда заканчивается регистрацией моделей и приёмочной
проверкой. RAGFlow держит у пользователя один сеанс: если в это время войти в
веб-интерфейс под суперпользователем, команда сама войдёт заново, а
веб-интерфейс попросит войти ещё раз.

**Назад на один узел** — для обслуживания узла или если он надолго выключен:

```bash
sudo ragspark llm qwen-3.8-27b-nvfp4
```

Эмбеддинги и реранкер снова запускаются на головном узле. Узел продолжает
работать, его половина ждёт; `sudo ragspark stop` на узле её останавливает.

**Перезагрузки и сбои.** Каждый узел при загрузке запускает свой стек, в любом
порядке; половины находят друг друга. Веб-интерфейс открывается через минуту-две
после загрузки головного узла, чат — примерно через 6 минут.
`ragspark-watch.timer` запускает `ragspark watch` на обоих узлах каждые 30 с и
перезапускает половину, которая зависла или потеряла партнёра: падение одной
половины восстановилось само за 6,5 минуты. Пока узел выключен, чат, поиск и
индексация не работают; веб-интерфейс и документы доступны.

**Предохранитель памяти.** Та же команда останавливает — не перезапускает —
половину своего узла, если две проверки подряд свободно меньше 4 GiB памяти:
узел, которому не хватило памяти, не падает, а перестаёт отвечать до
перезагрузки. Другая половина после этого ждёт. `sudo ragspark status`
показывает, когда сработал предохранитель; выясните, что заняло память, и
выполните `sudo ragspark start` на этом узле. Журнал присмотра:
`sudo journalctl -u ragspark-watch.service`.

**Порт 29501.** В режиме stack головной узел слушает порт 29501 на всех адресах:
там встречаются половины LLM (TCPStore из torch, его нельзя привязать к одному
адресу). Пока LLM работает, порт доступен из локальной сети — в доверенной сети
это принято (D12). Установщик брандмауэр не меняет; чтобы оставить порт только
кабелю, на головном узле:

```bash
sudo iptables -I INPUT -p tcp --dport 29501 ! -s 192.168.100.0/24 -j DROP
sudo ip6tables -I INPUT -p tcp --dport 29501 -j DROP
```

Половины работают по IPv4 на кабеле; при других адресах кабеля поменяйте
подсеть. Проверено на работающей паре: из локальной сети порт больше не
отвечает ни по IPv4, ни по IPv6, а по кабелю принимает и новые соединения —
они и нужны половинам, чтобы найти друг друга после перезапуска. Для `127.0.0.1`
порт тоже закрывается — половины этот адрес не используют. Правила действуют
до перезагрузки: сохраните их средствами своего брандмауэра, например пакетом
`iptables-persistent`.

**Удаление** одинаково на обоих узлах: `sudo ragspark uninstall`. Перед
удалением узла переключите головной узел на один Spark.

## Бэкапы и восстановление

Доступны с `f6b70d1` (локальные копии) и `e09da62` (настройка второго узла,
включая исправление прав каталога). Административные команды выполняются с
`sudo`. Копии содержат пароли и документы: доступ должен оставаться только у root.

### Что сохраняется

Головной узел сохраняет данные MySQL, MinIO, Elasticsearch и Valkey, свой `.env`
и манифест установки в `/srv/ragspark/backups/ragspark-YYYYmmdd-HHMMSS`.
В `backup.json` записаны ссылки на образы, размеры и SHA256. Сжатие — zstd в один
поток, при его отсутствии gzip. Веса моделей, Docker-образы, кэши компиляции
и ОС не входят в копию. Это бэкап данных, а не образ машины.

На время копирования останавливаются RAGFlow и четыре базы; контейнеры моделей
продолжают работать. По умолчанию команда ждёт завершения разбора документов до
60 минут, затем отказывает, если разбор продолжается или его состояние не удалось
проверить. После остановки RAGFlow выполняется повторная проверка. Запускаются
обратно только ранее работавшие сервисы. На первой небольшой рабочей копии перерыв
составил 66,5 с; с ростом данных он увеличится.

```bash
sudo ragspark backup
sudo ragspark backup --list
sudo ragspark backup --schedule on
```

`backup --wait-minutes 0` сразу отказывает при активном разборе документов.
`backup --dir /path/to/copies` меняет локальный каталог для этой команды;
ночной таймер всегда использует `/srv/ragspark/backups`.

Таймер запускается в **03:30 по системному часовому поясу головного узла**.
Пропущенная ночь не наверстывается при загрузке. Отключение:
`sudo ragspark backup --schedule off`. В каждом хранилище сохраняется последняя
копия каждого из последних **7 различных дней и 4 календарных недель**; берётся
объединение этих наборов, поэтому копий не обязательно 11. Копии с суффиксом
`-before-restore` автоматически не удаляются.

### Копирование на второй Spark

Настройка явная, на уже установленных head и node; локальные бэкапы работают и
без неё. Нужны SSH-клиент и `ssh-keygen` на head, SSH-сервер на node, `rsync` на
обоих, `/usr/bin/rrsync` на node и связь по кабелю. В примерах head —
`192.168.100.10`, node — `192.168.100.11`.

1. Получите **открытый** Ed25519 host key узла через уже доверенное
   административное SSH-соединение или его локальную консоль:

   ```bash
   cat /etc/ssh/ssh_host_ed25519_key.pub
   ```

   На head создайте `~/backup-node-known-hosts` с одной строкой:
   `192.168.100.11 ssh-ed25519 BASE64_PUBLIC_HOST_KEY`. Последнее поле замените
   проверенным ключом, без комментария. Непроверенное сканирование сети не
   устанавливает доверие к ключу.
2. На head:

   ```bash
   sudo ragspark backup --setup-remote sender --peer 192.168.100.11 --source-ip 192.168.100.10 --host-key-file ~/backup-node-known-hosts
   sudo cat /var/lib/ragspark-backup/id_ed25519.pub
   ```

   Через административное соединение перенесите только напечатанный **открытый**
   ключ отправителя в `~/backup-sender.pub` на node. Закрытый ключ остаётся на head.
3. На node:

   ```bash
   sudo ragspark backup --setup-remote receiver --source-ip 192.168.100.10 --public-key-file ~/backup-sender.pub
   ```

   Создаётся отдельный аккаунт `ragspark-backup`, ограниченный кабельным IP head
   и принудительной командой, без sudo и дополнительных групп. Ключ разрешает
   загрузку в `backup-incoming` и запрос квитанции; оболочка, скачивание бэкапов
   и удаление принятых копий запрещены.
4. На head создайте и проверьте первую копию до включения ночного расписания:

   ```bash
   sudo ragspark backup --wait-minutes 0
   sudo ragspark backup --sync
   sudo ragspark status
   ```

   На node команда `sudo ragspark backup --list` показывает принятые копии.
   После проверки включите ночной таймер на head, если он ещё не включён.

Сначала передаются архивы, последним — `backup.json`. Каждые 30 с root-служба
узла независимо проверяет входящие файлы и публикует закрытую копию в
`/srv/ragspark/backups`; квитанция содержит имя и SHA256 метаданных. Отправитель
сообщает об успешной репликации только после совпадения квитанции. Успех локального
бэкапа сам по себе не доказывает наличие второй копии. При сбое передачи локальная
копия сохраняется; повтор выполняется ежечасно или командой `backup --sync`,
без остановки RAGFlow. Каждое хранилище независимо выполняет ротацию.

Через `/srv/ragspark` на node разрешён проход; `backup-incoming` доступен только
приёмщику и root, хранилище принятых копий — только root. Служебные ключи и
настройки лежат в `/var/lib/ragspark-backup`. Принятую копию нельзя перезаписать
входящей копией с тем же именем. Автоочистки незавершённых/отклонённых загрузок и
квоты пока нет. На диске архивы не зашифрованы; SSH защищает передачу. Второй Spark
не заменяет копию за пределами площадки.

### Проверка работы

На head:

```bash
sudo ragspark backup --list
sudo ragspark status
systemctl list-timers --all ragspark-backup.timer ragspark-backup-sync.timer
sudo journalctl -u ragspark-backup.service -u ragspark-backup-sync.service -n 100 --no-pager
```

На node:

```bash
sudo ragspark backup --list
systemctl list-timers --all ragspark-backup-receive.timer
sudo journalctl -u ragspark-backup-receive.service -n 100 --no-pager
```

Если передача не подтверждена, проверьте кабель, закреплённый host key и службу
приёмщика, затем повторите `backup --sync`. Не ослабляйте ограничения SSH.
Изменение существующих systemd units и перечитывание systemd во время работы
моделей требуют процедуры из раздела «GPU после перезагрузки systemd»; setup
отказывает при изменении существующих backup units, а не перечитывает их молча.

### Восстановление на head

Восстановление заменяет текущие данные приложения. Выберите окно обслуживания,
прекратите новые загрузки документов и выберите полную копию через `backup --list`.
Ссылки на установленные образы RAGFlow и баз должны точно совпадать с записанными
в копии. При потере head сначала подготовьте совместимую установленную систему,
отдельно обеспечив образы и веса: бэкап не автоматизирует восстановление машины.

Если копия осталась только на node, администратор должен безопасно перенести весь
именованный каталог на head, сохранив содержимое и доступ только root. Для этого
нужны административные учётные данные: служебный ключ загрузки намеренно не может
читать хранилище. Не распаковывайте архивы вручную в рабочие тома.

```bash
sudo ragspark restore ragspark-YYYYmmdd-HHMMSS
```

Замените пример выбранным именем либо укажите полный путь к каталогу копии.
Команда проверяет архивы и контрольные суммы до остановки сервисов, проверяет
свободное место и запрашивает подтверждение. Затем создаёт страховочную копию
`-before-restore`, восстанавливает четыре тома и выбранные секреты баз/приложения
из `env`, запускает ранее работавшие сервисы. Сохранённый манифест не заменяет
манифест установки, выбор модели или настройки хоста. При ошибке восстановления
или запуска выполняется попытка возврата к страховочной копии и прежней
конфигурации. SIGKILL и отключение питания такая обработка внутри процесса не покрывает.

После этого проверьте `sudo ragspark status`, вход в веб-панель, наборы данных,
поиск документов и ответ чата. До завершения проверки сохраняйте страховочную
копию. См. [VALIDATION.ru.md](VALIDATION.ru.md), §19: проверено изолированное
восстановление четырёх сервисов данных; рабочая команда `ragspark restore` и
полное восстановление веб-приложения на практике не выполнялись.

Удаление RAGSpark отключает backup timers/services, но сохраняет архивы,
служебные ключи и аккаунт приёмщика. Их удаление — отдельное действие администратора.

## Удаление

```bash
sudo ragspark uninstall
```

Удаляет контейнеры и **все данные** (документы, пользователей, чаты), службу,
команду, `/opt/ragspark`, а также образы и веса моделей, которые скачал
установщик. Образы, веса и каталоги, существовавшие до установки, остаются.
Чтобы переустановить без повторного скачивания:

```bash
sudo ragspark uninstall --keep-images --keep-models
```

Если Docker не может удалить стек, удаление останавливается и сохраняет
`/opt/ragspark/compose/.env`: в нём единственная копия паролей баз данных.

## Если что-то пошло не так

| Симптом | Что делать |
|---|---|
| проверка не проходит | в сообщении сказано, что изменить; повторить — `sudo ./install.sh check` |
| образ не скачивается или зависает | медленный реестр: зеркало ([BUILD.ru.md](BUILD.ru.md)); запустите установщик снова, он продолжит |
| веса не скачиваются | `HF_ENDPOINT` или прокси в командной строке `sudo`, токен через `--preserve-env=HF_TOKEN` («Установка»); или скопируйте веса в каталог заранее |
| шаг 10 не проходит | `sudo ragspark status`, затем `sudo ragspark logs <сервис>`; [COMPOSE.ru.md](COMPOSE.ru.md), раздел о неполадках |
| режим stack: чат перестал отвечать | `sudo ragspark status` на обоих узлах; см. «Режим stack» |
| приёмочная проверка не проходит | в её выводе указана проваленная проверка; `sudo ragspark logs ragflow`; повторить — `sudo ragspark acceptance` |
| ответ занимает минуту и больше | так и должно быть на Medium и выше (см. «Уровни рассуждений»); Naive отвечает за секунды |
| что-то другое | `/opt/ragspark/install.log` |

## Разработка

Установщик — обычный Python (только стандартная библиотека) в
[installer/](../installer/). Тесты в [tests/](../tests/) прогоняют его целиком
без GPU и root: поддельные команды `docker`, `systemctl` и `nvidia-smi`
записывают, что делает установщик, `docker compose config` уходит в настоящий
Compose, а приёмочную проверку обслуживает имитация API RAGFlow.

```bash
RAGSPARK_TEST_COMPOSE=/path/to/docker-compose python3 -m unittest discover -s tests
```

Без `RAGSPARK_TEST_COMPOSE` сквозные тесты пропускаются.
