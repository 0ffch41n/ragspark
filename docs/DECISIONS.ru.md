# RAGSpark — запись решений

[English version](DECISIONS.md)

Результат этапа 1. Для каждого решения указано **что**, **почему**, **как** и
**риски**. Факты проверены по первоисточникам **1 октября 2026 года**; перед
любым обновлением версий их нужно проверить заново.

---

## D1. Имя — RAGSpark

- **Что:** проект, репозиторий, команда CLI, каталог установки и префикс
  контейнеров: `ragspark`, `/opt/ragspark`, `ragspark-<сервис>`.
- **Почему:** описательное имя без чужих товарных знаков. «DGX» — товарный знак
  NVIDIA, а «DGX Station» — их продукт, поэтому в имени они не используются.
  Продукты NVIDIA упоминаются только описательно: «для NVIDIA DGX Spark».
- **Как:** имя задаётся в одном месте, всё остальное выводится из него.

## D2. Лицензия — Apache-2.0, только собственный код

- **Что:** `LICENSE` (Apache-2.0) в корне.
- **Почему:** разрешительная, с патентной оговоркой, совместима с RAGFlow
  (Apache-2.0).
- **Как:** весь код пишется с нуля. Файлы и фрагменты из других проектов не
  копируются, поэтому чужие уведомления об авторских правах не наследуются.
  Стороннее ПО — RAGFlow, Elasticsearch, MySQL, Valkey, форк MinIO, vLLM —
  работает отдельными контейнерами под собственными лицензиями. Образ RAGFlow
  собирается из официальных исходников с правками RAGSpark, каждая из которых
  перечислена в D3 и [BUILD.ru.md](BUILD.ru.md); изменения в коде RAGFlow
  помечены комментариями `ragspark:` с именем скрипта правки.
- **Риск:** если когда-нибудь скопировать сторонний файл, придётся сохранить его
  уведомления — избегать этого или фиксировать здесь.

## D3. Ядро — RAGFlow 0.27.2, собственная сборка под arm64

- **Что:** сервер RAGFlow: разбор документов (DeepDoc), разбиение на фрагменты,
  поиск, чат со ссылками на источники, веб-интерфейс.
- **Почему эта версия:** ветка 0.27.x — последняя на Python; следующая мажорная
  версия (1.0) переписана на Go. 1.0.0-rc1 вышел 29 сентября 2026 года, и его
  Go-образ не поддерживается как штатная цель сборки на Linux arm64: он зависит
  от нативных библиотек, выпущенных только под x86-64. Код 0.27.x
  поддерживается в отдельной ветке `0.27.x` для исправлений.
- **Почему своя сборка:** RAGFlow публикует только x86-образы; пользователям
  arm64 предлагается собирать самим. Руководство по сборке требует на arm64
  xgboost 1.6.0 и unixODBC.
- **Как:** сборка из тега `v0.27.2` на DGX Spark (нативно arm64, без эмуляции),
  редакция slim (без встроенных моделей эмбеддингов — их даёт vLLM), публикация
  в GHCR как `ghcr.io/0ffch41n/ragspark-ragflow`, ссылка по хешу. Образы, из
  которых официальный Dockerfile собирает по плавающим тегам (`ubuntu:24.04`,
  `infiniflow/ragflow_deps:latest`), закреплены по хешу, так что повторная
  сборка берёт ту же основу и те же файлы данных. Рецепт:
  [BUILD.ru.md](BUILD.ru.md).
- **Опубликовано:** `0.27.2-arm64-r7` (29 октября 2026 года),
  `sha256:21c32fb9b8a54f02920f8bfc689166dbf8a6b0bc42b60a2d51baa86072f2d881`, —
  первый образ со всеми правками ниже. Он заменил `0.27.2-arm64-r6`
  (21 октября 2026 года,
  `sha256:16ba7dd9d03ae8d6a8d9f819e6c7e62d78874dfeb27367bbec536da02ea40fe9`,
  правки 1–7), `0.27.2-arm64-r5` (20 октября 2026 года,
  `sha256:a34a9f1f1009442497f50da91691edbc1dc19dea4cea7a73c9673a0000f61375`,
  правки 1–6), `0.27.2-arm64-r4` (19 октября 2026 года,
  `sha256:1ed7725f5932a4799591104b5efd1d1ed7f50984e070be24ed4251d27341e0f8`,
  правки 1–5), `0.27.2-arm64-r3` (14 октября 2026 года,
  `sha256:8d08d824a9b248fceba8a0c5885aaf3cef7f24c7137ec87154aef53031c22e5a`,
  собран раньше трёх последних изменений правки 4 и двух её исправлений не
  несёт — см. [BUILD.ru.md](BUILD.ru.md)), `0.27.2-arm64-r2` (8 октября
  2026 года,
  `sha256:4232ddbb513cff48c51864f081f6b82d37371927dea70bb01a200c6994f70dcc`,
  правки 1–2) и `0.27.2-arm64-r1` (1 октября 2026 года,
  `sha256:1bf5fc0031bff2d775dc8bc1626b2820f9b658b43696a9bb4bdc02a8304f0660`,
  правка 1).
- **Отличия от официальной сборки** — восемь, каждое вносит скрипт, который
  отказывается работать, если не находит ожидаемый код:
  1. Шаги Chrome и ChromeDriver выполняются только на x86_64: архивы в
     `ragflow_deps` являются x86-сборками и на arm64 не запускаются. Функции с
     браузером (например, веб-краулер в агентах) на arm64 недоступны.
  2. Реранкер получает исходный текст фрагмента (`r2`). Официальный код готовит
     текст для реранкера функцией `remove_redundant_spaces()`, которая удаляет
     все пробелы после нелатинских букв, — русский фрагмент приходит в реранкер
     одним длинным словом, и оценки падают в 2–3 раза. См. D15 и
     [VALIDATION.ru.md](VALIDATION.ru.md); будет отправлено разработчикам RAGFlow.
  3. Векторный поиск больше не требует совпадения слов (`r3`). Официальный
     код передаёт полнотекстовый запрос в kNN как фильтр, и оцениваются только
     фрагменты, где есть слова вопроса; RAGFlow не приводит русские слова к
     общей форме, и вопрос, сформулированный не так, как в документе, не
     находит ничего. Собственная функция RAGFlow, снимающая этот фильтр,
     закомментирована; правка её вызывает. См. D19.
  4. Двенадцать исправлений агентного конвейера чата (`r3`, `r4`), D19.
  5. Поле ввода чата начинает с уровня рассуждений «Naive» вместо «Low»
     (`r3`), D19.
  6. Три исправления, благодаря которым читаются сканы и русские PDF (`r5`),
     D14: DeepDOC сохраняет текстовый слой русской страницы, вызовы зрения
     идут при температуре 0, а нарезка не разрывает markdown-таблицы.
  7. Проверка здоровья возвращает соединение с базой в пул (`r6`). В
     официальном коде проба держала соединение из пула, пока собственный
     `close_stale(age=30)` RAGFlow не закрывал его из-под рабочего потока, и
     при проверке здоровья Docker раз в 15 с каждая третья проверка писала
     переподключение. См. [VALIDATION.ru.md](VALIDATION.ru.md), раздел 11.
  8. Фрагменты DOCX сохраняют разделитель между абзацами, которые они
     объединяют (`r7`). Официальный код режет каждый абзац по разделителю
     набора, выбрасывает разделитель и соединяет кусочки встык, поэтому
     последнее слово одного абзаца сливалось с первым словом следующего
     (`lm-sensorsgit`, `H100nvidia`) — в том, что читает LLM, в цитатах и в
     поиске по словам. PDF нарезается другим кодом и не затронут. Документы,
     проиндексированные до `r7`, сохраняют склеенный текст, пока их не
     разберут заново. См. [VALIDATION.ru.md](VALIDATION.ru.md), раздел 13.
- **Проверено (1 октября 2026 года):** сборка без изменений завершилась на DGX
  Spark; с собственным compose RAGFlow сервер показал `v0.27.2`, отдал
  веб-интерфейс, а Elasticsearch, MySQL, Valkey и объектное хранилище были
  в состоянии healthy.
- **Риски:**
  - 0.27.x в долгосрочной перспективе тупиковая ветка. Поэтому версия RAGFlow —
    сменный компонент; переход на 1.0 — отдельное решение, когда появится
    поддержка arm64.
  - Миграция данных 0.27.2 → 1.0 необратима: перед ней обязателен проверенный
    бэкап.
  - 1.0 меняет состав стека: Valkey → Apache Kvrocks, добавляется ClickHouse.

## D4. Поисковый движок — Elasticsearch 8.11.3

- **Что:** хранилище фрагментов, полнотекстового (BM25) и векторного поиска.
- **Почему:** эту версию закрепляет RAGFlow 0.27.x; Infinity на Linux arm64
  официально не поддерживается.
- **Как:** официальный arm64-образ; явный лимит памяти (на GB10 память общая с
  GPU); на этапе 6 каталог архивируется только после остановки Elasticsearch
  и остальных сервисов данных (D21), а не во время их работы. Snapshot API
  эта реализация бэкапа не использует.

## D5. Объектное хранилище — pgsty/silo

- **Что:** хранилище исходных загруженных файлов.
- **Почему:** MinIO перестал публиковать образы; репозитории на Docker Hub
  удалены в сентябре 2026 года, а анонимное скачивание с Quay из сети
  развёртывания было отклонено (проверено 28 сентября 2026 года). Сам
  RAGFlow 0.27.2 закрепляет `pgsty/silo:RELEASE.2026-08-06T00-00-00Z` —
  поддерживаемый форк MinIO от pgsty.
- **Как:** используем версию, которую закрепляет RAGFlow; наличие arm64
  подтверждено.
- **Запасной план:** любое другое S3-совместимое хранилище, которое
  поддерживает RAGFlow.

## D6. Инференс — vLLM, официальные образы, свой для каждой модели

- **Что:** OpenAI-совместимые серверы для LLM, модели эмбеддингов и реранкера.
- **Почему:** NGC (`nvcr.io`) отвечал HTTP 403 на любой запрос из сети
  развёртывания, включая выдачу токенов. Официальные образы `vllm/vllm-openai`
  с Docker Hub — штатный путь для DGX Spark, а специфика Spark — в рецепте
  модели, теге образа и флагах запуска.
- **Как:**
  - у каждой записи каталога свой образ, закреплённый по хешу — самым новым
    моделям иногда нужны отдельные образы, а у части FP4-ядер на sm_121 есть
    пробелы;
  - веса тоже закреплены: у каждого `vllm serve` стоит `--revision` с коммитом
    репозитория Hugging Face, который проверялся, а установщик скачивает и
    проверяет именно этот снимок — репозиторий, изменившийся под тем же
    именем, не меняет установку;
  - модели-пулеры (эмбеддинги, реранкер) запускаются с нейтральным entrypoint
    (`/usr/bin/env`), потому что entrypoint образа — `vllm serve`;
  - с драйвером cgroup `systemd` в Docker команда `systemctl daemon-reload`
    может отозвать доступ к GPU у работающих контейнеров (известная проблема
    NVIDIA Container Toolkit). Установщик не меняет настройки Docker:
    `ragspark check --gpu-reload` проверяет машину, а переход на `cgroupfs`
    описан в [INSTALL.ru.md](INSTALL.ru.md) (D18). На DGX OS 7.5 с Docker
    29.6.2 проверка прошла с драйвером `systemd` (9 октября 2026 года),
    поэтому он остаётся;
  - одно исключение: LLM режима stack, DeepSeek V4, работает на образе
    сообщества, потому что официальные пока не запускают её на GB10 (D20).

## D7. Эмбеддинги и реранкер

- **Что:** `deepvk/USER-bge-m3` (русская доработка bge-m3, контекст 8192) и
  `BAAI/bge-reranker-v2-m3`.
- **Почему:** проверены на DGX Spark; вместе занимают около 3 GB памяти.
- **Роль реранкера:** только он отличает «ответ в документах есть» от «ответа
  нет». Модель эмбеддингов оценивает посторонний вопрос так же высоко, как
  настоящий ответ (0,58 против 0,56–0,62), поэтому без реранкера ответ «в базе
  знаний этого нет» не срабатывал бы никогда (D15).
- **Важно:** модель эмбеддингов фиксируется для базы знаний; её смена означает
  переиндексацию. Это должно быть в документации.

## D8. Настройка моделей — через API RAGFlow

- **Что:** после установки в RAGFlow уже настроены LLM, эмбеддинги и реранкер,
  и они выбраны по умолчанию. Никаких ручных шагов в интерфейсе.
- **Почему через API:** механизм `user_default_llm` в `service_conf.yaml`
  объявлен устаревшим и не поддерживается в открытой версии RAGFlow после
  переделки каталога моделей в 0.26; каждый пользователь настраивает свои
  экземпляры моделей сам.
- **Как:** установщик создаёт администратора, входит через API и регистрирует
  модели. В 0.27 интерфейс провайдеров моделей переделан, поэтому форматы
  запросов снимаются с живой установки 0.27.2 до написания автоматизации.
- **Администратор:** при первом запуске служба администрирования создаёт
  суперпользователя с адресом из `DEFAULT_SUPERUSER_EMAIL` (в RAGFlow по
  умолчанию `admin@ragflow.io`; RAGSpark использует `admin@ragspark.local`) и
  паролем из `ADMIN_DEFAULT_PASSWORD`. Установщик задаёт случайное значение,
  поэтому гонки за первую регистрацию нет. Проверено: суперпользователь входит
  в обычный веб-интерфейс (1 октября 2026 года), заданный адрес работает
  (8 октября 2026 года).
- **Пользователи:** экземпляры моделей принадлежат конкретной учётке, поэтому
  модели настраиваются один раз у администратора, а остальные приглашаются
  через **Team**. Открытая регистрация отключается переменными
  `REGISTER_ENABLED=0` и `ENABLE_REGISTER=0` (проверено: кнопка регистрации
  исчезает).
- **Проверено (6 октября 2026 года):** последовательность запросов снята с
  веб-интерфейса и автоматизирована в
  [tools/ragflow_models.py](../tools/ragflow_models.py); проверено на живой
  системе, включая пересоздание удалённого экземпляра. Сами запросы перечислены
  в [VALIDATION.ru.md](VALIDATION.ru.md).
- **Модели по умолчанию хранятся по идентификатору.** После удаления и
  пересоздания экземпляра модель по умолчанию указывает на удалённую модель —
  интерфейс показывает голый идентификатор с предупреждением. Скрипт сравнивает
  идентификаторы, а не имена, и переназначает.
- **Реранкер по умолчанию применяется не везде:** проверка поиска и новые чаты
  создаются без него. Установщик задаёт его явно в создаваемых чатах (D15).
- **Смена LLM (этап 4):** переименовать модель RAGFlow не умеет, а чаты и
  модели по умолчанию ссылаются на неё по идентификатору записи, поэтому
  `ragspark llm` добавляет новую модель в те же экземпляры, переводит на неё
  модели по умолчанию, чаты, датасеты и документы сканов и отключает старую
  модель — обратная смена включает её снова ([TOOLS.ru.md](TOOLS.ru.md)).
  Модель эмбеддингов на месте не меняется никогда: индекс каждого датасета
  построен ею.
- **Одно исключение из API:** RAGFlow 0.27.2 не показывает настройки RAPTOR и
  графа в записях датасетов и документов своего API, а обновление настроек
  парсера документа без RAPTOR удаляет его собственные. Чтобы их сохранить,
  скрипт читает настройки документа через сервисы RAGFlow в контейнере — только
  чтение — и отправляет RAPTOR обратно через API без изменений; документ,
  настройки которого прочитать не удалось, остаётся как есть. Проверено на
  тестовой установке в обе стороны ([VALIDATION.ru.md](VALIDATION.ru.md),
  раздел 15).
- **Один сеанс на пользователя:** вход выдаёт новый токен сеанса и обрывает
  прежний сеанс пользователя, поэтому вход суперпользователя в другом месте —
  в веб-интерфейсе, из другого инструмента, — пока работает установщик или
  `ragspark llm`, обрывает сеанс инструмента. Тогда `ragflow_models.py` и
  `acceptance.py` входят заново и повторяют запрос, один раз: запрос,
  отклонённый с HTTP 401, ничего не изменил. Сеанс веб-интерфейса в ответ
  обрывается, и он просит войти снова. Найдено при переключении на режим stack
  ([VALIDATION.ru.md](VALIDATION.ru.md), раздел 18).

## D9. Каталог моделей

- **Что:** [catalog/models.yaml](../catalog/models.yaml) — по записи на модель:
  репозиторий, доля памяти, варианты контекста, вызов инструментов,
  поддерживаемые режимы, замеры, лицензия, пометка `validated`. Готовая к
  запуску запись ссылается на свой файл compose, в котором лежат образ, его хеш
  и флаги vLLM (D17).
- **Как:** визард предлагает только модели, которые помещаются на обнаруженном
  железе в выбранном режиме, и показывает ожидаемые контекст и скорость. Веса
  моделей лежат в каталоге хоста вне томов Docker, поэтому переустановка не
  скачивает их заново.
- **Сделано (этап 4):** меню установщика перечисляет все LLM, у которых есть
  файл в `compose/llm/` и которые поддерживают устанавливаемый режим, со
  скоростью для одного пользователя, контекстом, памятью (долей обнаруженной
  памяти), инструментами, зрением, лицензией и статусом; модель по умолчанию из
  каталога — первой. `--yes` берёт модель по умолчанию, `./install.sh --llm
  list` печатает меню. План перечисляет все модели, которые будут скачаны, с
  лицензиями. На одном DGX Spark помещается любая готовая LLM, поэтому
  проверка железа — это режим и наличие файла LLM; правило для памяти появится
  вместе с моделями, которым оно нужно ([INSTALL.ru.md](INSTALL.ru.md),
  [VALIDATION.ru.md](VALIDATION.ru.md), раздел 15).
- **Правило:** `validated: true` — только после прохождения приёмочной проверки
  на реальном железе. Лицензия модели показывается до скачивания.

## D10. Режим stack — два узла, одна большая LLM (этап 5)

- **Что:** два DGX Spark, соединённые напрямую кабелем QSFP (200 Гбит/с, MTU
  9000, RoCE на обеих половинах порта). *Головной* узел держит RAGFlow, его
  базы и одну половину LLM; *узел* запускает другую половину, эмбеддинги и
  реранкер. Тензорный параллелизм делит одну LLM на оба узла, поэтому
  помещается модель вдвое больше той, что вмещает один.
- **Почему:** второй узел нужен только ради модели, которую один не
  запустит. Вариант с двумя отдельными LLM, по одной на узел, рассмотрен и
  отклонён: отвечают они не лучше одной.
- **Модель:** DeepSeek-V4-Flash-Vision-Exp — MoE на 284B, активных 13B, FP8 с
  экспертами в FP4, зрительный модуль и встроенная черновая модель, лицензия
  MIT. Она помещается, если эмбеддинги и реранкер переезжают на узел: 79,5 GiB
  весов и 12 GiB KV-кеша на каждом узле. Вдвое быстрее LLM по умолчанию, на
  тестовых наборах RAGSpark отвечает так же, читает сканы; её знания
  заканчиваются примерно маем 2025 года ([VALIDATION.ru.md](VALIDATION.ru.md),
  раздел 17). Рассмотрены и отложены: MiniMax M2.5 и Qwen3-235B (на двух узлах
  не быстрее 27B на одном), GLM-5.3-Flash (не оставляет памяти для RAGFlow),
  MiMo-V2.6-Flash (медленнее на обычном тексте, требует много правок vLLM).
- **Как:**
  - собственный многоузловой запуск vLLM (`--nnodes 2`, половина узла с
    `--headless`) вместо Ray, хранилище объектов которого отнимает память,
    лишней у узлов нет. NCCL сам находит обе половины порта и IPv4-адрес RoCE
    на кабеле;
  - обе половины наследуют одно описание сервиса из `compose/ranks/`, поэтому
    всегда работают с одним образом, весами и флагами;
  - RAGFlow по-прежнему обращается к `vllm-llm`, `vllm-embed` и `vllm-rerank`;
    в режиме stack эти имена на головном узле — пересылки на кабель, поэтому
    настройки моделей в RAGFlow одинаковы в обоих режимах
    ([COMPOSE.ru.md](COMPOSE.ru.md), «Режим stack»);
  - узел ставится командой `install.sh --role node`; `sudo ragspark llm` на
    головном узле переключает работающую установку между режимами и переносит
    эмбеддинги и реранкер вместе с ней ([INSTALL.ru.md](INSTALL.ru.md),
    «Режим stack»);
  - сломанную пару vLLM сама не чинит. Политика перезапуска Docker `always` и
    `ragspark watch` — таймер на обоих узлах каждые 30 с — перезапускают
    половины. В той же команде есть предохранитель памяти: он останавливает
    половину, когда на узле остаётся меньше 4 GiB, раньше, чем узел перестанет
    отвечать;
  - веса читает загрузчик vLLM по умолчанию. `instanttensor`, на одном узле
    в 20 раз быстрее, с двумя половинами исчерпал память обоих узлов
    (VALIDATION, раздел 17).
- **Состояние:** на собственной паре RAGSpark работает с 11 ноября 2026 года,
  после того как падение одной половины и перезагрузка обоих узлов прошли без
  чьей-либо помощи (VALIDATION, раздел 18). По умолчанию каталог предлагает
  LLM для одного узла (D16): базовый продукт — один DGX Spark.
- **Ограничения:** для ответов нужны оба узла. Когда узел выключен,
  веб-интерфейс и сохранённые документы доступны, но ответы, поиск и
  индексация не работают, пока `sudo ragspark llm <LLM режима single>` не
  запустит всё на головном узле — обычные 7–10 минут смены LLM. Запуск пары
  занимает около 10 минут в первый раз и 5–6 минут потом.

## D12. Инженерные принципы

1. Установщик не меняет хост сверх того, что объявляет.
2. Удаление — зеркало установки, по манифесту созданных ресурсов.
3. В сеть смотрит только веб-вход; остальные порты привязаны к `127.0.0.1`.
   Он работает по обычному HTTP и рассчитан на доверенную сеть; TLS, где он
   нужен, даёт обратный прокси перед ним (принято после ревью безопасности
   2 ноября 2026 года). Одно исключение в режиме stack: порт 29501 на
   головном узле, где встречаются две половины LLM (TCPStore из torch),
   слушает все адреса — привязать его к одному torch не позволяет — и доступен
   из локальной сети. Принято на тех же условиях 11 ноября 2026 года; в
   [INSTALL.ru.md](INSTALL.ru.md), «Режим stack», есть правило брандмауэра,
   которое оставляет его только кабелю. Все остальные порты режима stack
   привязаны к адресу на кабеле.
4. Установка завершена, только когда RAG-запрос вернул ответ со ссылкой.
5. Реестры ненадёжны: офлайн-пакет и зеркало образов — базовые функции.

## D13. Доступ к реестрам

- **Что:** откуда и как скачиваются образы.
- **Почему:** 1 октября 2026 года Docker Hub из сети развёртывания завершал
  рукопожатие TLS за 15–20 секунд, а Docker ждёт не больше 10. GitHub, PyPI,
  GHCR и `mirror.gcr.io` в то же время отвечали быстрее 0,2 секунды. IPv6 до
  Docker Hub отказывал мгновенно и причиной не был.
- **Как:**
  - предварительная проверка замеряет скорость ответа реестров, отдельно по
    IPv4 и IPv6, а не только их доступность;
  - зеркало реестра (`mirror.gcr.io`) — необязательное объявленное изменение
    `/etc/docker/daemon.json`; оно записывается в манифест установки и
    откатывается при удалении;
  - собственные образы RAGSpark хранятся в GHCR.

## D14. Разбор документов — текстовый слой PDF, зрение для сканов

- **Что:** как PDF превращается в текст перед разбиением на фрагменты.
- **Решение:** парсер PDF **Naive** — собственный текстовый слой PDF, в коде он
  называется «Plain Text», — для PDF, у которых этот слой есть. У
  **отсканированного** PDF текстового слоя нет; его парсер — зрение самой LLM:
  работающая Qwen 3.8 зарегистрирована второй раз как зрячая модель
  `ragspark-vision` (`r5`). DeepDOC для русских документов не используется.
- **Почему:** распознаватель DeepDOC не умеет выдавать русский текст: в его
  словаре (`rag/res/deepdoc/ocr.res`) 6623 записи, из них 6277 — иероглифы и
  лишь одна из 33 строчных русских букв, поэтому кириллица превращается в
  латинские двойники (`Pa3beM` вместо «Разъем»). Кроме того, DeepDOC
  выбрасывает текстовый слой целой страницы,
  если больше 40% её символов — знаки препинания ASCII из встроенных
  подмножеств шрифтов (так срабатывают точки-заполнители в оглавлении), и
  распознаёт страницу как картинку. На русской инструкции в 39 страниц:

  | Парсер | Доля кириллицы | Искажённых слов | Найдено вопросов |
  |---|---|---|---|
  | DeepDOC | 0,665 | 194 | 4 из 8 |
  | Naive | **0,835** (= текстовый слой) | **0** | 5 из 8 → 8 из 8 с D15 |

- **Сканы:** та же инструкция, превращённая в скан (каждая страница — картинка,
  текстового слоя нет), замер [tools/rag_eval.py](../tools/rag_eval.py):

  | Парсер | Доля кириллицы | Искажённых слов | Найдено вопросов | Отклонено вопросов без ответа |
  |---|---|---|---|---|
  | Naive | 0,000 (текстового слоя нет) | 0 | 0 из 8 | — |
  | DeepDOC | 0,000 | 1066 | 0 из 8 | — |
  | зрение, `r5` | **0,818** | **2** | **8 из 8** | **2 из 2** |

  Для зрения понадобились три правки RAGFlow, все в `patch_scans.py` (D3,
  отличие 6): DeepDOC считает кириллицу текстом, когда решает, искажена ли
  страница; вызовы зрения идут при температуре 0 — при чатовых 0,7 одна и та же
  страница каждый раз расшифровывалась по-своему и иногда теряла таблицы, на их
  месте появлялись заглушки картинок; нарезка держит markdown-таблицу вместе с
  заголовком в одном фрагменте — раньше она резала таблицы по бюджету токенов, и
  строки без шапки не находились. Подробности: [VALIDATION.ru.md](VALIDATION.ru.md),
  раздел 10.
- **Компромиссы:** Naive превращает таблицы в строки — читаемо, поиск работает —
  и не читает сканы. Зрение читает страницу примерно за 17 с (инструкция заняла
  11 мин против 6 с по текстовому слою) и на время индексации делит LLM с чатом;
  в ячейках из одних символов (матрицы из ●) бывают мелкие ошибки, а скриншоты
  внутри страницы могут превратиться в заглушки картинок.
- **Открыто:** замерено на скане, сделанном из цифрового PDF (150 dpi, оттенки
  серого, JPEG); настоящий скан с перекосом и шумом бумаги ещё предстоит замерить.

## D15. Настройки поиска — реранкер, вес векторов 0,7, порог 0,1

- **Решение:** реранкер `bge-reranker-v2-m3` включён, вес векторного сходства
  **0,7**, порог сходства **0,1**, кандидатов для реранкера 64, top N 8,
  с правкой 2 из D3.
- **Почему:** итоговая оценка = вес слов × совпадение слов + вес векторов ×
  оценка реранкера. Совпадение слов для русского работает слабо — окончания, а
  60% этой оценки дают точные пары соседних слов, — поэтому решать должен
  реранкер. На 8 вопросах с ответом и 2 без ответа, после правки 2:

  | Настройка | Ответов найдено | Вопросов без ответа отсеяно |
  |---|---|---|
  | по умолчанию RAGFlow (0,3 / 0,2), реранкер | 6 из 8 | 1 из 2 |
  | реранкер, 0,7 / 0,2 | 7 из 8 | 2 из 2 |
  | **реранкер, 0,7 / 0,1** | **8 из 8** | **2 из 2** |
  | без реранкера, 0,7 / 0,2 или 0,5 | 8 из 8 | 0 из 2 |

- **Как:** установщик задаёт эти значения в создаваемых чатах. Настройки
  страницы проверки поиска в интерфейсе не сохраняются, поэтому тем, кто создаёт
  чаты сам, документация говорит их выставить.
- **Риск:** измерено на одном документе и 10 вопросах; запас ниже 0,1 пока не
  измерен. Приёмочная проверка перепроверяет каждую установку.
- **Начиная с `r3`** векторный поиск находит и фрагменты без общих слов с
  вопросом (правка 3 в D3, D19). Та же матрица на том же руководстве дала те
  же итоги в каждой настройке: реранкер с порогом 0,1 по-прежнему отклоняет
  оба вопроса без ответа.

## D16. LLM по умолчанию — Qwen 3.8 27B NVFP4 с MTP

- **Решение:** `unsloth/Qwen3.8-27B-NVFP4` на официальном образе vLLM 0.27.1,
  предсказание нескольких токенов (MTP) с 3 спекулятивными токенами;
  рассуждения выключены, а параметры выборки (температура 0,7, top-p 0,8,
  top-k 20) и предел ответа 8192 токена заданы на сервере (D19). Флаги — в
  [compose/llm/qwen-3.8-27b-nvfp4.yaml](../compose/llm/qwen-3.8-27b-nvfp4.yaml).
- **Почему:** сильная открытая модель своего класса, Apache-2.0, встроенный
  вызов инструментов, скорость почти не падает на длинном контексте. В русских
  проверках (30 ответов) ни разу не перешла на другой алфавит и правильно
  ссылалась на источники.
- **Почему этот чекпоинт (с 28 октября 2026 года):** до этого по умолчанию
  стоял `Inferact/Qwen3.8-27B-NVFP4` — та же модель, квантованная иначе.
  Профиль показал, что 62% шага генерации у него уходило на веса, оставленные
  в bf16: самые большие проекции линейного внимания во всех 48 линейных слоях
  и `lm_head` на 2,5 ГБ, который черновики MTP читают трижды за шаг. В
  чекпоинте unsloth они хранятся в FP8: 23,4 ГБ вместо 26,4, **на 29% больше
  токенов в секунду** на одного пользователя на рабочем Spark (27,2 вместо
  21,1), та же доля принятых токенов MTP (74%) и такие же или лучшие ответы во
  всех проверках через RAGFlow ([VALIDATION.ru.md](VALIDATION.ru.md),
  раздел 12). Прежняя пометка, что у чекпоинта Inferact выше принятие MTP
  (0,897 против 0,788), не подтвердилась.
- **Замерено:** 27,2 токена/с на пользователя при контексте в 1 тысячу
  токенов, 26,0 при 8 тысячах; 8 параллельных запросов — суммарно около 137
  токенов/с. Первые замеры, на чекпоинте Inferact, — в разделе 1 VALIDATION
  (10,2 токена/с без MTP, 17,1 с MTP). Рассуждения выключены на сервере,
  потому что RAGFlow не передаёт этот переключатель: с рассуждениями тот же
  ответ занял 1116 токенов и 108 секунд вместо 101 токена и 10 секунд.
- **Компромисс:** длинный запрос читается медленнее: первый токен на запросе
  в 8 тысяч токенов приходит через 6,4 секунды вместо 4,9. На ответах в
  несколько сотен токенов более быстрая генерация всё равно выигрывает.
- **Альтернатива (этап 4):** Qwen 3.6 35B-A3B, смесь экспертов примерно с 3 млрд
  активных параметров: примерно в 4 раза быстрее (107,6 ток/с), те же ответы на
  Naive и Low, но на Medium и выше чаще даёт только часть ответа из двух частей
  ([VALIDATION.ru.md](VALIDATION.ru.md), раздел 14). Gemma 4 26B-A4B отложена:
  нет вызова инструментов для агентных уровней, и она медленнее обеих.

## D17. Запуск — собственный compose RAGSpark

- **Что:** [compose/](../compose/) заменяет compose RAGFlow: один проект
  `ragspark` с RAGFlow (образ `r3`), Elasticsearch, MySQL, объектным
  хранилищем, Valkey и тремя сервисами vLLM. LLM описана в отдельном файле в
  `compose/llm/`, который выбирается через `COMPOSE_FILE` в `.env`.
  Руководство: [COMPOSE.ru.md](COMPOSE.ru.md).
- **Почему не compose RAGFlow:** он публикует порт каждого сервиса
  (Elasticsearch, MySQL, объектное хранилище, Valkey, API, службы
  администрирования и MCP), поставляется с общими паролями по умолчанию,
  жёстко задаёт часовой пояс Asia/Shanghai и ничего не знает о моделях.
- **Как:**
  - один опубликованный порт — nginx RAGFlow, по умолчанию 80; всё остальное
    только во внутренней сети (D12). С ноября 2026 года модели и базы данных —
    в сети с пометкой `internal` (`ragspark-backend`), без пути наружу; выход
    наружу остался только у `ragflow`;
  - порядок запуска через проверки готовности: сервисы vLLM по одному
    (эмбеддинги, реранкер, LLM), базы данных параллельно с ними, RAGFlow
    последним. vLLM рассчитывает размер кеша по памяти, которую измеряет при
    запуске; на общей памяти то, что в этот момент заняла другая стартующая
    модель, засчитывается ему самому, поэтому одновременный запуск может
    оставить модель без места под кеш;
  - политика перезапуска `on-failure:5`: упавший контейнер перезапускается.
    Запуск при загрузке — служба systemd, которая выполняет compose (D18).
    Часть контейнеров Docker при загрузке всё же поднимает сам — см. D18, — и
    служба восстанавливает порядок;
  - случайные пароли для каждой установки (`init-env.sh`, `.env` с правами
    600). Ключ подписи сессий задаётся явно (`RAGFLOW_SECRET_KEY`); иначе
    RAGFlow создаёт его сам и хранит в Valkey;
  - адрес суперпользователя настраивается: служба администрирования RAGFlow
    читает `DEFAULT_SUPERUSER_EMAIL`, когда создаёт учётку
    (`admin/server/auth.py`); RAGSpark использует `admin@ragspark.local`;
  - часовой пояс хоста во всех контейнерах (`RAGSPARK_TZ`; переменные, которые
    может задать и оболочка, начинаются с `RAGSPARK_`, потому что compose
    предпочитает значение из оболочки значению из `.env`);
  - vLLM запускается без выхода в интернет (`HF_HUB_OFFLINE=1`): веса берутся
    только из кеша хоста, подключённого только на чтение, и запуск не зависит
    от Hugging Face. Отправка статистики выключена (`VLLM_NO_USAGE_STATS`,
    `DO_NOT_TRACK`). У каждого контейнера vLLM свой `/dev/shm` вместо общего
    пространства IPC хоста, а модели эмбеддингов и реранкера работают без
    `--trust-remote-code`: их закреплённые ревизии — стандартный XLM-RoBERTa
    без кода;
  - журналы ограничены 5 × 20 MB на контейнер; каждый образ закреплён хешем
    ([tools/pin_images.py](../tools/pin_images.py)).
- **Другие отличия от compose RAGFlow:** база MySQL создаётся через
  `MYSQL_DATABASE` вместо подключаемого `init.sql`; `hostname: ragflow`
  сохраняет идентификатор обработчика задач при пересоздании контейнера;
  проверки готовности строже (кластер Elasticsearch хотя бы в состоянии
  yellow; `/api/v1/system/healthz` RAGFlow через nginx, который проверяет
  MySQL, Valkey, Elasticsearch и хранилище); нет профилей, сервера на Go, NATS
  и TEI.
- **Проверено (8 октября 2026 года):** с пустыми томами стек запустился в
  задуманном порядке за 9 мин 10 с (LLM — 7 мин 11 с; при перезапуске с кешем
  компиляции — 332 с); слушает только порт 80; контейнеры работают в часовом
  поясе хоста; заданный адрес суперпользователя работает; скрипт
  зарегистрировал модели на пустой базе; результаты поиска совпали с этапом
  3.1. Модели запустились без освобождения файлового кеша. Подробности:
  [VALIDATION.ru.md](VALIDATION.ru.md), раздел 6.

## D18. Установщик — одна программа на Python, манифест и служба systemd

- **Что:** `install.sh` запускает [installer/](../installer/) — программу на
  Python 3.10+, которая использует только стандартную библиотеку. Та же
  программа, установленная как `/usr/local/bin/ragspark`, умеет `status`,
  `start`, `stop`, `restart`, `logs`, `acceptance`, `check` и `uninstall`.
  Руководство: [INSTALL.ru.md](INSTALL.ru.md).
- **Почему Python, а не shell:** проверки со структурированным результатом,
  манифест в JSON, сообщения на двух языках и тесты, которые прогоняют всю
  установку с поддельными `docker` и `systemctl`. В DGX OS есть Python 3.12;
  на хост ничего не ставится.
- **Как:**
  - проверки выполняются до любых изменений. Проблемы, при которых
    продолжение повредило бы существующие данные, — стенд, запущенный
    вручную, тома прежнего стенда, `/opt/ragspark` или файл службы, созданные
    не установщиком, — останавливают установку даже с `--force`;
  - файлы ставятся в `/opt/ragspark`; настройки создаёт `init-env.sh` (D17);
  - всё созданное — каталоги, файлы, служба, скачанные образы (по точной
    ссылке), скачанные репозитории моделей — записывается в `manifest.json`,
    и удаление убирает ровно это (D12). Образы, веса и каталоги, которые были
    до установки, остаются. Если `docker compose down` не прошёл, удаление
    останавливается и сохраняет `.env` — единственную копию паролей;
  - каждый шаг идемпотентен; прерванная установка продолжается с настройками,
    с которыми её начали;
  - веса проверяются без сети и скачиваются временным контейнером из образа
    vLLM (`huggingface_hub`), только в тех форматах, которые загружает vLLM;
    `HF_TOKEN`, `HF_ENDPOINT` и переменные прокси передаются дальше;
  - служба — `Type=exec` с `RemainAfterExit`: она выполняет
    `docker compose up -d --wait` и не задерживает загрузку. Перед этим она
    останавливает контейнеры проекта, которые работают, но не готовы. Docker
    при старте заново применяет политики перезапуска, и `on-failure`
    перезапускает каждый контейнер, чей последний код выхода не 0 (moby,
    `daemon/daemon.go`, `restartmanager`): убитый после таймаута остановки
    (137), Elasticsearch (143) или все сразу после отключения питания (255).
    Запущенные вместе, модели оставляют друг друга без памяти;
  - systemd перезагружается до запуска моделей; при продолжении установки
    стек сначала останавливается. `/etc/docker/daemon.json` не меняется:
    `ragspark check --gpu-reload` запускает контейнер с GPU, перезагружает
    systemd и снова проверяет GPU, а переход на `cgroupfs` — описанный ручной
    шаг (D6);
  - установка завершается приёмочной проверкой (D12): одностраничный русский
    PDF (вымышленная памятка, воспроизводимо генерируется
    `acceptance/make_sample.py`) индексируется с настройками RAGSpark (D14,
    D15), и чат должен ответить на два вопроса нужными фактами, со ссылкой на
    источник и без знаков CJK, а на вопрос, ответа на который в документе
    нет, выдать свой текст «нет ответа»; первый вопрос задаётся ещё раз на
    уровне рассуждений Low (D19). База знаний и чат остаются как пример.
    Проверка также создаёт, один раз, чат «Ассистент» без базы знаний для
    общих вопросов и проверяет, что он отвечает (с `--skip-acceptance`
    выполняется только эта часть);
  - сообщения на английском и русском (D11); журнал с правами 600 и без
    паролей; проверки здоровья берут пароли из окружения контейнера, а пароль
    Valkey не попадает в его командную строку.
- **Проверено (9 октября 2026 года):** установка с нуля на машине этапа 3.2,
  где уже были образы и веса, — стек за 9,4 мин, приёмочная проверка пройдена
  за 16 с; GPU сохраняется после `systemctl daemon-reload`; после
  перезагрузки Docker сам запустил два контейнера, служба остановила их и
  запустила стек по порядку примерно за 7 мин; `stop` / `start` — 6,2 мин.
  Проверка весов без сети переписана после того, как она запросила из сети
  файлы, не нужные vLLM. Подробности: [VALIDATION.ru.md](VALIDATION.ru.md),
  раздел 7.
- **Проверено повторно (20 октября 2026 года), этап 3.4:** установка с нуля на
  вычищенной машине из свежего клона `main`, образ подтянут из GHCR по digest —
  стек за 9,4 мин, приёмочная проверка пройдена за 29 с, а режимы чата
  воспроизвели результаты раздела 8 на всех уровнях. Подробности:
  [VALIDATION.ru.md](VALIDATION.ru.md), раздел 9.

## D19. Режимы чата — Naive по умолчанию, агентные уровни работают

- **Что:** переключатель уровня рассуждений под полем ввода чата RAGFlow.
  Уровень 0, «Naive», — классический путь: поиск с настройками D15, один
  вызов LLM или текст «нет ответа» без него. Уровни 1–4 (Low, Medium, High,
  Ultra) отвечают через агентный конвейер RAGFlow: внешняя модель с
  инструментом `rag`, затем ключевые слова, поиск, промежуточный черновик и
  проверка достаточности — с каждым уровнем больше.
- **Найдено (этап 3.3):** с русскими документами и Qwen 3.8 27B ни один
  агентный уровень не работал. Low зависал на десять минут; Medium на всё
  отвечал «нет ответа»; перефразированный вопрос не находился ни на одном
  уровне.
- **Решение:** образы `r3` и `r4` устраняют причины (все в RAGFlow, ни одной в
  модели), а переключатель начинает с **Naive**: те же ответы на наборах
  вопросов RAGSpark за 3 с вместо 15 с у Low и до 1–2 мин у Medium и High.
  Остальные уровни остаются в переключателе для вопросов, которым нужно
  несколько поисков.
- **Исправления:**
  - kNN без полнотекстового фильтра (правка 3 в D3): вопрос, сформулированный
    не так, как в документе, теперь находит его;
  - служебные вызовы конвейера получают `frequency_penalty 0.5` и предел в
    2048 токенов (`RAGSPARK_HELPER_FREQUENCY_PENALTY`,
    `RAGSPARK_HELPER_MAX_TOKENS`): при температуре 0,1 и без предела запрос
    ключевых слов зацикливался в 9 случаях из 30, пока не заполнялся контекст
    в 64k;
  - Medium, High, Ultra: флаг «ничего не найдено», выставленный в начале,
    никогда не сбрасывался, и шаг ответа отбрасывал найденное;
  - агентный поиск использует реранкер чата и оценивает вопрос, а не вопрос
    с дописанными ключевыми словами;
  - в чате с базами знаний внешняя модель отвечает только через инструмент
    `rag` — раньше на «столицу Австралии» она отвечала сама, однажды
    «Сидней»; чаты без базы знаний сохраняют исходный промпт;
  - заметка для внешней модели («[Research status] …») убирается из ответа;
  - ограничение длины ответа vLLM по умолчанию — 8192 токена
    (`max_new_tokens`), потому что RAGFlow вырезает `max_tokens` из всех
    запросов;
  - фрагменты не сужаются по кириллическим ключевым словам: после каждого
    поиска конвейер оставлял только те фрагменты, где встречается одно из
    ключевых слов вопроса — с учётом основы для слов на латинице, но буква в
    букву для всего остального, — и русские словоформы выбрасывали как раз
    тот фрагмент, в котором был ответ;
  - в чате с базами знаний первый круг обязан вызвать `rag`: при
    `tool_choice "auto"` внешняя модель пропускала инструмент в 3 вопросах
    Low из 9, и её собственный текст возвращался как ответ;
  - бюджет исследования задаётся переменной `RAGSPARK_AGENTIC_BUDGET_S` и по
    умолчанию равен 300 с вместо жёстко прописанных 180 с: на скорости этой
    модели (~17 ток/с) High и Ultra расходовали потолок внутри первого круга
    исследования, и граф синтезировал ответ по неполным данным. Бюджеты
    отдельных вызовов не изменились, поэтому увеличенный потолок даёт больше
    кругов исследования, а не более долгие вызовы;
  - планировщик и верхние уровни пишут поисковые запросы на языке вопроса: ни
    в одном из трёх промптов, порождающих запросы, язык не был указан, и
    русский вопрос дробился на английские подзадачи («knowledge base backup
    schedule»), которые в русском корпусе не находят ничего — единственная
    поломка, которую не лечат ни реранкер, ни правка фильтра kNN;
  - проверка достаточности переносит элементы `claims`, не являющиеся
    объектами: она читает ответ как список объектов-утверждений, а модель
    иногда отвечает `"claims": ["c0", …]`, и `item.get()` на строке поднимал
    `AttributeError` наружу из графа — `_bounded` ловит только
    `TimeoutError`, поэтому Ultra заканчивался трассировкой вместо ответа.
- **Проверено (12–13 и 19 октября 2026 года):** каждый набор правок сначала
  вносился в работающий контейнер — `r2` для первых восьми, `r3` для
  последних четырёх — и замерялся
  [tools/mode_eval.py](../tools/mode_eval.py) на примере приёмочной проверки и
  руководстве этапа 3.1. Со всеми правками каждый уровень отвечает 7/7 и
  по-прежнему отклоняет вопрос, ответа на который в документах нет; только с
  первыми восемью Medium давал 6/7, High — 5/7, Ultra — 6/7. Образ, который
  несёт все двенадцать, — `r4`. Подробности:
  [VALIDATION.ru.md](VALIDATION.ru.md), раздел 8.
- **Что нужно знать:** агентные уровни пишут ответ сами, как только находят
  фрагменты, поэтому на вопрос, ответа на который в документах нет, Medium
  может написать своими словами «в документах нет информации о …» вместо
  текста «нет ответа» или вывести ответ из найденного.

## D20. Образ vLLM от сообщества для DeepSeek V4 на GB10

- **Что:** LLM режима stack работает на
  `ghcr.io/timothystewart6/vllm-gb10:v0.31.0-gb10.1` — vLLM 0.31, собранный под
  sm_121a с CUDA 13.2, FlashInfer 0.7.0.post1 и b12x 1.5.0, — закреплённом по
  дайджесту в `compose/ranks/`. Исключение из официальных образов D6.
- **Почему:** ни один официальный выпуск vLLM пока не запускает DeepSeek V4 на
  GB10 (sm_121). Этот образ собирает CI из закреплённых исходников, лицензия
  MIT, а его автор проверил DeepSeek V4 Flash с тензорным параллелизмом на
  двух узлах GB10. Образ, который называет рецепт самого vLLM для DGX Spark,
  существует только как `:latest`, собранный из основных веток vLLM и NCCL,
  так что по закреплению нельзя понять, что в нём.
- **Условия:** новый дайджест — повтор окна этапа 5: скорость, уровни чата,
  сканы, падение одной половины ([VALIDATION.ru.md](VALIDATION.ru.md),
  разделы 17–18). Модели режима single остаются на официальных образах. Образ
  сообщества может исчезнуть: держите копию в зеркале реестра (D13). Заменить
  на официальный, как только выпуск vLLM поддержит модель на sm_121.

## D21. Бэкапы данных — остановка сервисов и проверенная вторая копия

- **Что:** закрытые для обычных пользователей копии MySQL, MinIO, Elasticsearch,
  Valkey, env головного узла и манифеста установки. Веса и образы нужны отдельно.
- **Согласованность:** RAGFlow и четыре базы останавливаются до архивации;
  работающий каталог Elasticsearch не архивируется. Разбор документов проверяется
  до и после остановки RAGFlow; модели продолжают работать. Принимаем перерыв
  веб-интерфейса ради простого, проверенного пути восстановления на тех же образах.
- **Расписание и история:** явное включение запуска в 03:30 местного времени,
  без наверстывания при загрузке; последняя копия за каждый из 7 различных дней
  и 4 календарных недель, объединение наборов. Страховочные копии перед
  восстановлением исключены из автоматической ротации.
- **Второй узел:** SSH по кабелю, закреплённый host key, отдельный ключ отправителя
  и ограниченный аккаунт приёмщика. Файлы поступают в недоверенный входящий каталог;
  root-процесс проверяет их, публикует закрытую копию и выдаёт квитанцию.
  Только совпавшая квитанция подтверждает репликацию. Ежечасный повтор не
  останавливает сервисы. Хранилища самостоятельно ведут историю; отправитель
  не может удалить принятые копии.
- **Восстановление:** проверка до остановки, точное совпадение ссылок на образы
  баз и RAGFlow, страховочная копия, восстановление данных и выбранных значений
  env, попытка отката при ошибке. Это не восстановление машины с нуля и не
  миграция между версиями RAGFlow.
- **Ограничения:** SSH шифрует передачу, но не архивы на диске. Нет внешней копии,
  квоты входящего каталога и автоочистки отклонённых загрузок. Потеря хоста/SIGKILL
  во время копирования или восстановления требует проверки администратором.
  Восстановление четырёх сервисов данных показано на изолированном стенде;
  рабочая CLI-команда restore и полное приложение ещё не проверялись. См.
  [VALIDATION.ru.md](VALIDATION.ru.md), §19 и [INSTALL.ru.md](INSTALL.ru.md),
  «Бэкапы и восстановление».

## Открытые вопросы

- **Сканы.** Читаются через зрение начиная с `r5` (D14), но замерены только на
  скане, сделанном из цифрового PDF; настоящий скан ещё предстоит замерить.
- **Auto-question и Keyword analysis.** Обе функции привлекают LLM для лучшего
  совпадения: вопросы к каждому фрагменту при индексации и ключевые слова к
  каждому запросу. Измерить пользу против дополнительного времени.
- **Сообщения разработчикам.** Ошибки RAGFlow, найденные на этапах 3 и 4,
  стоит отправить в ветку `0.27.x`: вход реранкера (правка 2 в D3), DeepDOC на
  кириллице (D14), фильтр kNN (правка 3 в D3), дефекты агентного конвейера
  из D19, удержанное соединение проверки здоровья (правка 7 в D3) вместе с
  самим `close_stale(age=30)`, который закрывает любое соединение, занятое
  дольше 30 с, в том числе посреди долгой транзакции, склейку фрагментов DOCX
  (правка 8 в D3) и обновление документа, которое удаляет настройки RAPTOR,
  невидимые в API (D8).
- **Обновление установки.** Установщик копирует свой код в `/opt/ragspark`
  один раз; более новая версия — например, `ragspark llm` на установке,
  сделанной до этапа 4, — попадает туда только ручным копированием файлов.
  Команда обновления — задача этапа 6.
- **Своп во время загрузки LLM режима stack.** Пока читаются веса, 16 GiB
  свопа на головном узле примерно на минуту заполняются целиком, хотя 30 GiB
  памяти остаются доступными: ядро выносит редко используемые страницы баз
  данных вместо того, чтобы освободить файловый кеш. Сбоев не было
  (VALIDATION, раздел 18); нужно проверить меньшее значение `vm.swappiness`.
- **Ultra.** Четвёртый уровень отвечает 7/7 на примере приёмочной проверки
  (`r4`), но его собственная отличительная черта всё ещё не проверена:
  инструменту графа знаний нужен граф, построенный при индексации, а ни в
  одном наборе вопросов RAGSpark его нет — уровень замеряли без него.
- **Лицензия драйвера ODBC.** Официальный Dockerfile ставит драйвер ODBC от
  Microsoft и принимает его лицензию. Проверить условия распространения для
  опубликованного образа — или убрать драйвер, если коннекторы к SQL Server не
  нужны.
