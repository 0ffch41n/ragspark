# Запуск RAGSpark через Docker Compose

[English version](COMPOSE.md)

Каталог [compose/](../compose/) запускает весь режим `single` на одном DGX
Spark: RAGFlow, его базы данных и три сервера моделей vLLM. Вместе с
`compose/node/` он запускает и режим `stack` на двух узлах (см. «Режим stack»
ниже). [Установщик](INSTALL.ru.md) выполняет шаги ниже и держит свою копию в
`/opt/ragspark/compose`; это руководство — для разработки и разбора
неполадок. Решение: D17 в [DECISIONS.ru.md](DECISIONS.ru.md), режим stack —
D10.

## Файлы

| Файл | Назначение |
|---|---|
| `compose/compose.yaml` | все сервисы, кроме образа и флагов LLM |
| `compose/llm/<модель>.yaml` | по файлу на LLM: образ, флаги vLLM, что регистрировать в RAGFlow |
| `compose/env.example` | шаблон настроек; `init-env.sh` делает из него `.env` |
| `compose/init-env.sh` | создаёт `.env` со случайными паролями и часовым поясом хоста |
| `compose/.env` | настройки и пароли этой установки (права 600, в git не попадает) |
| `compose/stack.yaml` | режим stack, головной узел: `vllm-llm`, `vllm-embed`, `vllm-rerank` становятся пересылками на кабель |
| `compose/relay.py` | пересылка: передаёт соединения на другой узел |
| `compose/ranks/<модель>.yaml` | LLM режима stack: образ, веса и флаги, общие для обеих половин |
| `compose/node/` | второй узел режима stack: свои `compose.yaml`, `llm/` и `.env` |

`COMPOSE_FILE` в `.env` соединяет `compose.yaml` с выбранным файлом LLM,
поэтому любую команду `docker compose` нужно запускать из каталога `compose/`.

## Сервисы

| Сервис | Образ | Роль | Память |
|---|---|---|---|
| `vllm-embed` | vLLM 0.27.1 | эмбеддинги, `deepvk/USER-bge-m3` | 5% общей памяти |
| `vllm-rerank` | vLLM 0.27.1 | реранкер, `BAAI/bge-reranker-v2-m3` | 3% |
| `vllm-llm` | из файла LLM | модель для чата (по умолчанию Qwen 3.8 27B NVFP4) | 50% |
| `es01` | Elasticsearch 8.11.3 | полнотекстовый и векторный индекс | до 8 GB |
| `mysql` | MySQL 8.0.40 | метаданные RAGFlow | — |
| `minio` | pgsty/silo | загруженные файлы | — |
| `redis` | Valkey 8 | очереди и кеш | 128 MB |
| `ragflow` | образ RAGSpark (`r7`) | веб-интерфейс, API, обработка документов | — |

Порт публикует только `ragflow`: его nginx на порту 80 (`RAGSPARK_HTTP_BIND`,
`RAGSPARK_HTTP_PORT`), который отдаёт и веб-интерфейс, и API по пути
`/api/v1`. Он же единственный сервис с выходом наружу (сеть `ragspark`).
Модели и базы данных — в сети `ragspark-backend` с пометкой `internal`: RAGFlow
обращается к ним по имени сервиса, а пути наружу у них нет. Контейнеры vLLM
получают веса только на чтение и собственный `/dev/shm` на 2 GB вместо общего
пространства IPC хоста.

## Порядок запуска

1. `vllm-embed`, затем `vllm-rerank`, затем `vllm-llm` — по одному, каждый
   ждёт, пока предыдущий сообщит о готовности.
2. `es01`, `mysql`, `minio` и `redis` стартуют сразу, параллельно с моделями.
3. `ragflow` стартует, когда всё перечисленное готово, поэтому он никогда не
   отправляет запрос модели, которая ещё загружается.

Модели запускаются по одной, потому что vLLM рассчитывает размер своего кеша
по памяти, которую измеряет во время запуска. На общей памяти то, что в этот
момент заняла другая стартующая модель, засчитывается ему самому, и маленьким
моделям не остаётся места под кеш.

Замерено 8 октября 2026 года, веса уже в кеше: весь стек — 9 мин 10 с;
эмбеддинги 36 с, реранкер 36 с, LLM 7 мин 11 с, RAGFlow около 45 с.
Перезапуск одной LLM занимает около 5,5 минут, потому что кеш компиляции
сохраняется между запусками.

## Первый запуск

Нужны Docker с NVIDIA runtime (в DGX OS есть и то и другое), локальные образы и
веса моделей в `/srv/ragspark/hf-cache`.

```bash
cd compose
./init-env.sh                       # создаёт .env; существующий не перезаписывает
sudo docker compose config --quiet  # проверяет файлы и .env
sudo docker compose up -d --wait --wait-timeout 2400
sudo docker compose ps
```

`init-env.sh` задаёт суперпользователя `admin@ragspark.local`; если нужен другой
адрес, измените `DEFAULT_SUPERUSER_EMAIL` в `.env` до первого запуска. Пароль —
`ADMIN_DEFAULT_PASSWORD` в `.env`. Оба значения читаются один раз, когда RAGFlow
создаёт суперпользователя.

Затем зарегистрируйте модели в RAGFlow и назначьте их моделями по умолчанию:

```bash
sudo docker compose exec -T ragflow \
  sh -c 'cd /ragflow && PYTHONPATH=/ragflow .venv/bin/python -' < ../tools/ragflow_models.py
```

и откройте в браузере `http://<адрес Spark>/`.

**Весов ещё нет в кеше?** vLLM запускается без выхода в интернет, с кешем
только на чтение, и останавливается, если файла не хватает. Установщик
скачивает веса заранее; вручную — для каждого репозитория из `vllm serve` и
его `--revision`:

```bash
sudo docker run --rm -v /srv/ragspark/hf-cache:/root/.cache/huggingface \
  --entrypoint hf <образ vLLM из compose.yaml> download <репозиторий> --revision <коммит>
```

## Повседневные команды

Все — из `compose/`:

| Задача | Команда |
|---|---|
| состояние | `sudo docker compose ps` |
| журнал одного сервиса | `sudo docker compose logs -f --tail 100 ragflow` |
| остановить всё, данные сохранить | `sudo docker compose down` |
| запустить снова | `sudo docker compose up -d --wait --wait-timeout 2400` |
| перезапустить один сервис | `sudo docker compose restart vllm-llm` |
| оболочка в RAGFlow | `sudo docker compose exec ragflow bash` |

После сбоя контейнеры перезапускаются. При загрузке Docker сам поднимает
только контейнеры, чей последний код выхода не 0, — все сразу и не по порядку.
Служба systemd из установщика останавливает их и запускает стек по порядку
([INSTALL.ru.md](INSTALL.ru.md), «Запуск при загрузке»). Без неё после
перезагрузки выполните `sudo docker compose stop`, затем `up`.

## Смена LLM

`sudo ragspark llm` показывает работающую LLM и остальные; `sudo ragspark llm
<имя>` меняет её ([INSTALL.ru.md](INSTALL.ru.md), «Команды»). Команда по
порядку:

1. скачивает образ и веса новой LLM, если их нет, — чат в это время отвечает;
2. указывает в `COMPOSE_FILE` в `.env` новый файл, останавливает `vllm-llm`,
   сбрасывает кэш страниц и запускает одну новую LLM (`up --no-deps vllm-llm`).
   На DGX Spark vLLM считает свою долю памяти по свободной памяти, а кэш только
   что прочитанных весов её скрывает. RAGFlow всё это время работает. Если новая
   LLM не стала healthy, снова запускается прежний файл. Когда она готова,
   `docker compose up -d --wait` пересоздаёт `ragflow`, в окружении которого
   записано имя модели; `ragflow` зависит от `vllm-llm`, поэтому обычный `up`
   держал бы его выключенным весь запуск LLM;
3. запускает `tools/ragflow_models.py`: новая модель добавляется в экземпляры
   `ragspark-llm` и `ragspark-vision`, на неё переходят модель чата по
   умолчанию, все чаты, датасеты и документы, которые разбирают сканы старой
   моделью, а старая модель отключается — переименовать модель RAGFlow не
   умеет, а чаты ссылаются на неё по id записи. Заново ничего не разбирается;
4. запускает приёмочную проверку.

Пока новая LLM запускается, чат не отвечает примерно 7–10 минут; веб-интерфейс,
датасеты и поиск работают, кроме примерно минуты, пока перезапускается `ragflow`. Вернуть
прежнюю — та же команда с её именем; её веса остаются на диске. Команда берёт
файлы LLM из установленной копии в `/opt/ragspark`: модель, добавленная в
репозиторий позже, появится, когда эти файлы обновятся. Модели эмбеддингов и
реранкера так не меняются: индекс поиска каждого датасета построен моделью
эмбеддингов.

## Режим stack

Два DGX Spark на прямом кабеле QSFP вместе запускают одну LLM (D10).
Настраивает их установщик ([INSTALL.ru.md](INSTALL.ru.md), «Режим stack»);
здесь — что где работает.

| Узел | Проект, каталог | Сервисы |
|---|---|---|
| головной | `ragspark`, `compose/`; `COMPOSE_FILE=compose.yaml:stack.yaml:llm/<модель>.yaml` | RAGFlow и его базы; `vllm-llm-rank`, одна половина LLM (сеть хоста, API на адресе кабеля, порт 8000); `vllm-llm`, `vllm-embed`, `vllm-rerank` как пересылки |
| узел | `ragspark-node`, `compose/node/`; `COMPOSE_FILE=compose.yaml:llm/<модель>.yaml` | `vllm-llm-rank`, другая половина (`--headless`); `vllm-embed` и `vllm-rerank` на адресе кабеля, порты 8001 и 8002 |

- **Адреса.** В каждом `.env` есть `RAGSPARK_HEAD_IP` (по умолчанию
  192.168.100.10), `RAGSPARK_NODE_IP` (192.168.100.11) и `RAGSPARK_CABLE_IF` —
  интерфейс, на котором они настроены. Режим stack слушает только кабель,
  кроме порта 29501 из torch на головном узле (D12).
- **Одно описание для обеих половин.** `compose/ranks/<модель>.yaml` содержит
  образ, веса и все флаги vLLM; `llm/<модель>.yaml` головного узла и
  `node/llm/<модель>.yaml` узла наследуют его и добавляют только номер
  половины. Пути в `extends` считаются от каталога проекта.
- **Пересылки.** RAGFlow обращается к тем же именам, что и в режиме single.
  `relay.py` (стандартная библиотека Python, пользователь `nobody`, без GPU)
  передаёт каждое соединение на кабель; пересылка готова, когда модель за ней
  отвечает на `/health`. RAGFlow пересылок не ждёт: когда узел выключен,
  веб-интерфейс и документы доступны, а ответы не работают.
- **Запуск.** Каждый узел при загрузке запускает свой проект, в любом
  порядке. Половины ждут друг друга на порту 29501 и затем вместе загружают
  веса: API отвечает примерно через 10 минут после первого запуска и через
  5–6 минут после следующих (кеш ядер хранится в томе `vllm-rank-cache`).
- **Упавшая половина.** Сама vLLM пару не чинит. Политика перезапуска Docker
  `always` перезапускает завершившуюся половину — потеряв партнёра, vLLM
  выходит с кодом 0, и `on-failure` оставил бы её остановленной.
  `ragspark watch`, таймер systemd на обоих узлах каждые 30 с, берёт на себя
  то, чего Docker не видит: на головном узле, пока API сообщает о готовности,
  он отправляет запрос на один токен и после двух неудач перезапускает
  половину; на узле перезапускает половину, если головной, уже побывав
  готовым, минуту недоступен. Падение половины на узле восстановилось само за
  6,5 минуты ([VALIDATION.ru.md](VALIDATION.ru.md), раздел 18).
- **Предохранитель памяти.** Тот же таймер останавливает — не перезапускает —
  свою половину, если две проверки подряд свободно меньше 4 GiB памяти.
  `sudo ragspark status` после этого называет время и объём памяти; выясните,
  что её заняло, и `sudo ragspark start` снова запустит половину. Без
  предохранителя узел, которому не хватило памяти, не падает, а почти
  замирает до перезагрузки (VALIDATION, раздел 17).
- **Смена режима** — `sudo ragspark llm <имя>` на головном узле. Перед
  запуском LLM режима stack пересылки заменяют местные эмбеддинги и
  реранкер; при возврате к LLM режима single они снова запускаются на
  головном узле. При каждой смене поиск останавливается примерно на минуту.
- **На узле** команды выше выполняются из `compose/node/`, или используйте
  `sudo ragspark status | start | stop | logs`; его статус ещё сообщает,
  отвечает ли половина головного узла.

## Данные

| Том | Содержимое |
|---|---|
| `ragspark_esdata` | поисковый индекс |
| `ragspark_mysql` | пользователи, базы знаний, чаты, настройки |
| `ragspark_minio` | загруженные документы |
| `ragspark_valkey` | очереди задач и кеш |
| `ragspark_ragflow-logs` | журналы RAGFlow |
| `ragspark_vllm-compile-cache` | результаты компиляции vLLM, ускоряют следующие запуски |
| `ragspark_vllm-rank-cache` | режим stack: кеш ядер половины головного узла |
| `/srv/ragspark/hf-cache` (каталог хоста) | веса моделей |

Проект узла `ragspark-node` хранит только кеши: `vllm-compile-cache` и
`vllm-rank-cache`.

`sudo docker compose down -v` удаляет все перечисленные тома — все документы,
пользователей и чаты. Веса в `/srv/ragspark/hf-cache` остаются. Храните `.env`,
пока существуют тома: базы данных принимают только те пароли, с которыми были
созданы.

Журнал каждого контейнера ограничен пятью файлами по 20 MB.

## Неполадки

| Признак | Причина и что делать |
|---|---|
| `up` останавливается с `dependency failed to start` | модель или база данных не стала готовой: `sudo docker compose ps -a` и журнал этого сервиса |
| сервис vLLM завершается с `Free memory on device … is less than desired` | память заняли другие процессы или файловый кеш. Посмотрите `free -g`; кеш освобождается командой `sudo sh -c 'sync; echo 3 > /proc/sys/vm/drop_caches'` |
| сервис vLLM завершается с `LocalEntryNotFoundError` или `offline mode` | весов нет в кеше — см. «Весов ещё нет в кеше?» |
| порт 80 занят | другой веб-сервер или старый стек; измените `RAGSPARK_HTTP_PORT` или остановите его |
| режим stack: чат не отвечает | `sudo ragspark status` на обоих узлах: должны работать обе половины. Если половину остановил предохранитель памяти — выясните, что заняло память, затем `sudo ragspark start` на этом узле |
| режим stack: после перезагрузки половины не находят друг друга | кабель: `ip -br addr` должен показать оба адреса кабеля; `sudo ragspark check` на головном узле проверяет кабель и узел |
